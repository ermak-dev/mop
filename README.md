# MOP. Master of Puppets

  <img src="docs/cover.jpg" width="100%" alt="обложка">
</p>

Рой агентов (папетов).  Мастер раздаёт задачи, папеты на узлах пула их делают.

## Термины

- Мастер (master): сессия на машине оператора, которая держит очередь задач трекера, раздаёт их папетам и принимает отчёты. Поднимается командой `mop master` в рабочей копии проекта.
- Папет (puppet): агент, который делает задачу. Живёт в tmux на узле пула, работает в своей рабочей копии, о результате отчитывается мастеру по шине.
- Узел (node): машина пула, на которой живут папеты. Либо машина с Linux, где папеты работают процессами в общей среде, либо гипервизор Proxmox, где каждый папет изолирован в контейнере LXC.
- Рабочая копия (workspace): собственный клон репозитория у папета на узле.
- Песочница (sandbox): то, в чём папет работает — образ контейнера или сам узел. Что в ней должно быть, проект описывает в `.mop/sandbox.yaml`, а что нужно на каждом старте — в `.mop/bootstrap.yaml`.
- Проект: один репозиторий в пуле. Папеты одного репозитория образуют срез пула, и мастер проекта видит только их.

## Установка

1\. Клонировать репозиторий, вывести команду наружу и настроить саму машину. Всё запускается через `mop <подкоманда>`.

```
git clone <адрес> ~/mop
sudo ln -s ~/mop/bin/mop /usr/local/bin/mop
mop setup
```

`mop setup` ставит ansible (Debian 13, через apt) и дальше плейбуком `deploy/self.yml` настраивает саму машину: rsync, git, pip и python-библиотеки mop. Узлам пула всё поставит `mop deploy`. На машине оператора, которая плейбуки пула не гоняет, — `mop setup --operator`.

2\. Настроить установку. Три файла, каждый копируется из примера и заполняется, в git они не попадают.

2.1. `.env`, настройки установки.

```
cp .env.example .env && chmod 600 .env
```

- `MOP_SERVER_LAN`, обязательная: адрес сервера в локальной сети. На него ходят и узлы, и мастер.
- `MOP_GIT_HOST`, обязательная: хост, с которого папеты клонируют проекты.
- `MOP_GIT_KEY`, по умолчанию первый из `~/.ssh/id_ed25519`, `~/.ssh/id_rsa` на сервере: ключ, под которым узлы клонируют проекты. Его публичную часть зарегистрируйте на `MOP_GIT_HOST` с правом чтения всех проектов пула; нет ключа — `ssh-keygen -t ed25519`.
- `Z_AI_KEY`, опционально: если используется модель `GLM` от z.ai

Весь словарь с текущими значениями показывает `mop config`.

2.2. `inventory.yaml`, машины и их роли, формат `Ansible`. Одна машина может быть в нескольких ролях.

```
cp inventory.yaml.example inventory.yaml
```

- `server`: Nomad-сервер и шина NATS. Машина оркестратора, с неё же запускают `mop deploy`.
- `puppet`: узлы пула, на них живут папеты.
- `proxmox`: узлы Proxmox, где папет живёт в контейнере LXC. Такой узел перечисляют и в `puppet`. Каждому гипервизору здесь задают свою `mop_pve_vmid_base`: из неё считается и срез сети тел, и адрес каждого тела, так что на общей базе две машины выдали бы один адрес двум разным телам.

2.3. `sandbox.yaml`, песочница установки: окружение папетов, общее для всех проектов. Это список задач ansible, он печётся в образ проекта и проигрывается на узлах, где тело равно узлу.

```
cp sandbox.yaml.example sandbox.yaml
```

- Тулчейн, ваши скиллы, ваши MCP-серверы.
- В примере лежит окружение чужой установки: выкиньте лишнее и впишите своё.
- Нужное одному проекту сюда не пишут, для этого есть `.mop/` в самом проекте.

3\. Развернуть пул. Один прогон ставит кластер Nomad, окружение узлов, шину с агентом и сторожем диска. Прогон идемпотентен, упавшее чинят повторным запуском.

```
mop deploy
```

4\. Раздать логин. `claude login` на сервере, затем `mop login` разносит логин claude.ai и ключи LLM по узлам пула.

5\. Проверить: `mop list` показывает пул и живых агентов, `mop doctor` даёт диагностику целиком.

6\. Подключить машину оператора, если это не сервер: клон mop, `mop setup --operator`, `.env` с `MOP_SERVER_LAN`, затем `mop join --user <имя>` — вход своим именем из `MOP_OPERATORS` сервера. Токен Nomad туда не едет: управление пулом идёт глаголами на шине (`docs/CLUSTER.md`). В инвентаре её нет, плейбуки пула она не гоняет.

## Подключение проекта

Проект должен быть доступен по git с `MOP_GIT_HOST`: узлы клонируют его сами.

1\. При необходимости положить в корень проекта каталог `.mop/` с двумя плейбуками ansible. Оба необязательны, многим проектам хватает общей песочницы установки из `sandbox.yaml`. Имя файла говорит, когда он играется.

1.1. `.mop/sandbox.yaml` печётся в образ контейнера (на узле, где папет живёт прямо в системе, играется при `mop deploy`). В `vars` можно запросить ресурсы для папета, в `tasks` поставить системные пакеты и тулчейн проекта. Всё тяжёлое — сюда: оно платится один раз на образ.

```yaml
---
- name: What the project bakes into its sandbox
  vars:
    MOP_MEM_MB: "8192"
    MOP_DISK_GB: "50"
    MOP_CORES: "4"
  tasks:
    - name: Native build prerequisites
      ansible.builtin.apt:
        name: [protobuf-compiler, libssl-dev]
        state: present
```

1.2. `.mop/bootstrap.yaml` играется сервером при каждом старте песочницы, перед запуском папета. Сюда идёт то, что часто меняется и в образ не печётся: env-файлы, ключи API, настройка окружения. Пути `src` — на сервере. Держите его в секундах: он идёт и при лечении залипшего папета. На сервер файл кладут `mop deploy` (из origin) и `mop add` с `mop bootstrap push` (из рабочей копии), подробности в `docs/BOOTSTRAP.md`.

Прежние имена `.mop/node.yaml` и `.mop/workspace.yaml` пока читаются как `sandbox.yaml` и будут сняты: переименуйте.

2\. Завести проект в пуле. Команда заводит проекту пользователя на шине и раздаёт креды мастеру и папетам. Какие проекты уже заведены, показывает `mop project list`; `mop deploy` настраивает машины и о проектах не знает.

```
mop project add git@git.example.org:team/project.git
```

Если у проекта есть `.mop`, задачи его песочницы проигрывают слои узла и тела — то есть `mop deploy`; команда об этом скажет.

3\. Только для гипервизоров: собрать образ проекта. Сборка впекает размеры и окружение из `.mop` в образ, дальше каждый папет клонируется из него. После правки `.mop` образ собирают заново. Без аргумента в рабочей копии проекта сборка берёт `.mop` из её файлов как лежат, без коммита и push, так правку манифеста проверяют до влития в master.

```
mop driver build
```

4\. Начать работу. `mop master` в рабочей копии проекта поднимает мастера с кредами проекта, `mop add` заводит папета. Результат виден в `mop list`.

## Использование

Запустите `mop master` в рабочей копии проекта. Поднимется claude code, который видит только папетов этого проекта: ростер, состояние, переписку.

В этой сессии скилл `/master` ведёт разбор и раздачу задач. Например:

```
> /master Дай мне на разбор первую задачу из трекера.
...
Я разобрал задачу, вот её суть и предложенный фикс. Одобряешь или правим?
...
> Одобряю
...
Задача одобрена, отдаю её в пул. Жду отчёта от папетов.
...
Задача выполнена, реализация проверена. Выдаю landing-токен.
...
Задача успешно приземлена в интеграционную ветку.
> Следующая задача
```

Скилл живёт в `skills/master`. Он держит очередь заявок трекера и разбирает их с вами по одной: суть, свидетельства, предлагаемый фикс. Ничего не уходит в работу без одобрения. Одобренное он раздаёт свободным папетам, каждый делает фикс в своём клоне и присылает отчёт. В интеграционную ветку изменения садятся по одному, через landing-токен, а полный гейт гоняется уже на интегрированном результате. Размер пула скилл держит сам: заводит папетов под одобренную работу, отпускает их, когда очередь кончилась, лечит залипших.

### Командная строка

Полный список подкоманд даёт `mop` без аргументов. Чаще прочего нужны:

```
mop list                   ростер в терминале (в сессии мастера то же даёт инструмент agents)
mop project list           какие проекты заведены в пуле
mop attach <имя>           живой терминал папета (ssh + tmux)
mop project add [origin]   завести новый проект (без origin — эта рабочая копия)
mop project delete <имя>   снять проект с пула
mop driver build [origin]  собрать образ проекта на гипервизорах; без аргумента берётся эта рабочая копия
mop node                   узлы пула: драйвер, проекты, ёмкость
mop web                    дашборд пула в браузере, http://<сервер>:9000/ (docs/WEB.md)
mop recycle <имя>          пересоздать папета на чистой рабочей копии
mop disk / mop gc          место на узлах, подробности в docs/GC.md
```

### Модели

`mop llm` перечисляет профили, которыми поднимают папетов, и показывает, чей ключ есть в `.env`. Профиль выбирают при создании папета (`mop add --llm профиль`) и для сессии мастера (`mop master --llm профиль`). `mop code --llm профиль` поднимает на том же профиле обычную сессию claude без проекта и без пула, когда нужна только модель.

Сейчас есть профили `claude` (подписка claude.ai) и `glm` (`Z_AI_KEY` в `.env`). Новый профиль добавляется файлом в `mop/llm/` по образцу.

### Место на узлах

`mop disk` показывает свободное место. `mop gc` пересоздаёт свободных папетов на узлах, где места не хватает, занятых не трогает. Мусор в рабочих копиях подрезает сторож на самом узле, подробности в [docs/GC.md](docs/GC.md).

## Если что-то сломалось

Диагностика: `mop doctor` в терминале или инструмент `doctor` в сессии мастера. `--fix` чинит то, что чинится само. Другой дороги на узел, кроме шины, нет: упавший агент и битые креды лечат повторным `mop deploy`.
