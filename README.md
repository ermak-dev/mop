# mop - Master Of Puppets

Пул claude-слейвов: управляющая машина (мастер) раздаёт задачи, а сессии
claude code на остальных машинах (слейвы, на узлах пула) их делают. Где
встаёт слейв, решает Nomad, сообщения между мастером и слейвами возит NATS.

Слейв живёт в tmux на узле и работает с собственной рабочей копией проекта.
Проект здесь называют шардом: слейвы одного репозитория образуют срез пула,
и мастер этого проекта видит только его, чужие для него не существуют.

## Что нужно

* Машины: одна всегда включённая под сервер (Nomad и шина) и сколько угодно
  узлов под слейвов. Узлом годится линукс семейства Debian, остальное плейбук
  ставит сам; слейв бронирует 8 ГБ памяти.
* Все машины под одним пользователем, узлы доступны управляющей машине по ssh.
* На управляющей машине: python3, ansible, git.
* claude code на узлах: с логином claude.ai или ключом LLM-провайдера.
* Инвентарь ansible с ролями-группами: `server` (сервер), `slave` (узлы
  пула) и `master` (управляющая машина). Заводится в корне проекта из
  `inventory.ini.example`, в git не попадает.

## Установка

1. Клонировать репозиторий и вывести команду наружу:

       git clone <адрес> ~/mop
       sudo ln -s ~/mop/bin/mop /usr/local/bin/mop

   Всё запускается через `mop <подкоманда>`: диспетчер настраивает окружение,
   файлы из `bin/` напрямую не вызываются.

2. Завести настройки и инвентарь:

       cp .env.example .env && chmod 600 .env
       cp inventory.ini.example inventory.ini

   В `.env` обязательная настройка одна: `MOP_SERVER_LAN`, адрес сервера в
   локальной сети. Из остального вписывают ключ LLM-провайдера (например,
   `Z_AI_KEY`), если слейвы работают не через claude.ai; что действует сейчас
   и откуда взялось каждое значение, показывает `mop config`. В инвентаре
   впишите машины и раскидайте их по ролям.

3. Развернуть пул:

       mop deploy

   Один прогон ставит всё в правильном порядке: кластер Nomad, окружение
   узлов, шину с агентом и сторожем диска. Прогон идемпотентен и всегда
   полный, чинить упавшее проще им же, чем выбором цели. Новый шард заводят
   аргументом: `mop deploy <git-origin>`. Окружение узлов берётся из
   `examples/homelab`, это установка автора (тулчейны, postgres) — под свои
   проекты правьте его.

4. Залогинить claude: `claude login` на управляющей машине, затем `mop login`
   раздаст логин claude.ai и ключи LLM на узлы пула.

Готовность проверяют `mop list` (пул собран, агенты живы) и `mop doctor`
(диагностика целиком).

## Использование

Петлю ведёт мастер-сессия со скиллом `/master`; терминал нужен, чтобы её
поднять, и остаётся запасным путём оператора.

### Мастер: `mop master` + скилл `/master`

В рабочей копии проекта `mop master` поднимает claude с кредами шарда:
сессия видит только слейвов этого проекта — ростер, состояние, переписку.
Скажи ей «запусти /master» — и она ведёт петлю управления (скилл живёт в
`skills/master`):

* держит очередь заявок трекера и разбирает их с тобой по одной: суть
  человеческим языком, свидетельства, предлагаемый фикс — ты одобряешь или
  правишь; ничего не уходит в работу без одобрения;
* диспатчит одобренное свободным слейвам: каждый делает фикс в собственном
  клоне на своём узле и присылает отчёт — отчёт и есть сигнал;
* пропускает приземления через landing-токен: в интеграционную ветку
  садится по одному изменению, полный гейт гоняется на интегрированном
  результате;
* сам держит размер пула: заводит слейвов под одобренную работу, отпускает,
  когда очередь кончилась, лечит залипших и следит за пайплайном.

Всё это — MCP-инструменты сервера `mop` (`agents`, `send`, `tail`, `pool`,
`slave`, `doctor`, `slash`, `login`; перечень и профили —
[docs/MCP.md](docs/MCP.md)). Мастеров на один проект можно держать несколько,
но landing-токен они не делят: очередь ведёт один.

### Терминал: что осталось вне сессии

Полный список подкоманд даёт `mop` без аргументов. Чаще прочего:

```
mop list                   ростер в терминале (в сессии — инструмент agents)
mop shards                 какие шарды уже заведены в пуле
mop attach <имя>           живой терминал слейва (ssh + tmux)
mop deploy <git-origin>    завести новый шард — проект в пуле
mop recycle <имя>          пересоздать слейва на чистой рабочей копии
mop disk / mop gc          место на узлах, подробности — docs/GC.md
```

### Модели

`mop llm` перечисляет профили, которыми поднимают слейвов, и показывает, чей
ключ есть в `.env`. Профиль выбирают при создании слейва (аргумент `llm`) и
для сессии мастера (`mop master --llm ПРОФИЛЬ`).

### Место на узлах

`mop disk` показывает свободное место, `mop gc` пересоздаёт свободных слейвов
на узлах, где его не хватает; занятых не трогает. Мусор в рабочих копиях
подрезает сторож на узле сам, подробности в [docs/GC.md](docs/GC.md).

## Если что-то сломалось

Диагностика — `mop doctor` в терминале или инструмент `doctor` в
мастер-сессии; `--fix` / `fix=true` чинит то, что чинится само. Дороги на
узел мимо шины нет: упавший агент и битые креды лечатся повторным
`mop deploy`.
