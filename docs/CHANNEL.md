# Канал сообщений claude code

Как программно послать сообщение в живую сессию claude code и как узнать, что
она его отработала. Это внутренний протокол claude code, разобран по бинарю
**2.1.251** и без публичных обещаний; если доставка вдруг ломается — смотреть
в первую очередь конверт `cross-session-message` и held-логику. Контракт
квитанций (§ «Квитанции») снят отдельно с **2.1.302** и привязан к этой
версии.

Реализация — `mop/session.py` (сокет, кадры, конверт) и `mop/client/channel.py`
(#148: маршрут по адресу, своя сессия, доставка тремя путями и вердикт);
фронтенды — команда `mop send` и инструмент `send` в `mop mcp`, оба только
рисуют вердикт. Помечено, что проверено на живой сессии, а что прочитано в
бинаре.

Канал использует только messaging inbox. Все локальные интерфейсы claude code
(inbox, daemon control, worker rendezvous и PTY) с их границами разобраны в
[CLAUDECODE](CLAUDECODE.md).

## Где сокет

У каждой сессии свой unix-сокет:

```
/run/user/<uid>/cc-socks/<pid>.sock
```

Путь пишется в файл сессии `~/.claude/sessions/<pid>.json`, поле
`messagingSocketPath`. Каталог выбирается по `XDG_RUNTIME_DIR`, с откатом на
`/tmp/cc-socks-<uid>/`. Если полный путь не влезает в 103 байта (лимит длины
пути unix-сокета), сессия уходит на запасной вариант.

Не путать с сокетом Chrome native host: он лежит в том же каталоге и с тем же
шаблоном имени, но говорит на другом протоколе — живая интерактивная сессия на
`ping` не ответит. Отличать по `messagingSocketPath` в файле сессии, а не по
имени файла.

Дочерние процессы сессии получают адрес и токен прямо в окружении — это
санкционированный вход, ничего искать не надо:

```
CLAUDE_CODE_MESSAGING_SOCKET=/run/user/1000/cc-socks/861028.sock
CLAUDE_CODE_MESSAGING_TOKEN=<childToken>
```

## Кадрирование

NDJSON: по одному JSON-объекту в строке, разделитель `\n`.

* строка длиннее **1 МиБ** — соединение рвут;
* первая полная строка должна прийти за **30 с**, иначе соединение закрывают;
* ответа в том же соединении не бывает: отправитель пишет и закрывает, а всё,
  что сессия хочет сказать в ответ, она шлёт отдельным соединением на адрес из
  поля `from`.

## Авторизация

Первой строкой — необязательный кадр:

```json
{"type":"auth","token":"<32 hex>"}
```

Токен лежит рядом с файлом сессии:

```
~/.claude/sessions/<pid>.<sha256(realpath пути сокета)>.key      (0600)
{"peerToken":"…","procStart":"…","pidDomain":"…"}
```

На linux и macos auth формально не обязателен (личность отправителя даёт
`SO_PEERCRED`), на windows обязателен. Но права разные: без токена сообщение
примут, а подписку `notify_when_idle` молча уронят. Поэтому токен (`peerToken`
из key-файла) стоит слать всегда; `childToken` из окружения — для собственных
потомков сессии.

## Сообщение

```json
{"msgV":1,
 "msg_id":"<uuid4>",
 "type":"user",
 "message":{"role":"user","content":"<текст, см. конверт ниже>"},
 "priority":"now|next|later",
 "from":"uds:/run/user/1000/cc-socks/<мой-pid>.sock"}
```

| поле | обязательность | смысл |
|---|---|---|
| `msgV` | нет | версия кадра, сейчас `1` |
| `msg_id` | нет | uuid4; по нему приходят квитанции |
| `message.content` | **да** | непустая строка, иначе кадр молча выбросят |
| `priority` | нет | `next` по умолчанию; `now` — вперёд очереди |
| `from` | нет | обратный адрес; без него сессия видит «unidentified» |
| `session_id` | нет | если указан и не совпал — кадр выбросят |
| `file_attachments` | нет | вложения (не проверялось) |

Сообщение кладётся в очередь как `{isMeta: true, skipSlashCommands: true,
skipAttachments: true}`. Отсюда ограничение: **слэш-команды через канал не
работают**, `/model` в тексте останется текстом; единственный способ выполнить
слэш-команду в чужой сессии — напечатать её в tmux-пейн (глагол `type`).

## Конверт: заявка о режиме прав

Сессия, запущенная с `--dangerously-skip-permissions`, не отдаёт модели
сообщение отправителя, не заявившего свой режим прав: кладёт его в
«held»-очередь и рисует диалог «Deliver / Deny». Для папета без человека за
терминалом это неотличимо от потери сообщения.

Заявка живёт не в полях кадра, а внутри `message.content`:

```
<cross-session-message from="uds:…" from-session="…" hop-chain="…" from-name="…" from-mode="bypass">
тело сообщения
</cross-session-message>
```

* все атрибуты необязательны, но **порядок фиксирован** — именно этот: приёмник
  разбирает конверт регуляркой и сверяет обратную сборку байт в байт;
  переставленные атрибуты не распознаются, и сообщение уезжает в held;
* `from-mode`: `bypass` | `prompting`; должен совпадать по классу с режимом
  приёмника, иначе held с причиной `mode-mismatch`;
* `from` — тот же `uds:`-адрес, что и в кадре, спецсимволы percent-кодируются
  (`/`, `:`, `.`, `-`, `_` остаются как есть);
* `from-session` — `[A-Za-z0-9_-]{1,80}`, `from-name` — без `"<>` и переводов
  строк, `hop-chain` — до 32 хешей через запятую (защита от петель пересылки).

Причины удержания, которые может назвать приёмник: `no-mode-asserted`,
`mode-mismatch`, `bypass-default`, `explicit-setting`, `managed-setting`,
`repo-setting`, `invalid-setting`.

Второй путь — со стороны приёмника, в его `settings.json`:

```json
{"crossSessionInbound": "accept"}
```

Значения: `accept` | `hold` | `refuse`. Managed- и repo-настройки могут только
ужесточать: собственный `accept` их не перебивает.

## Обратный канал

Чтобы получать ответы, надо самому слушать сокет. Адрес проверяют строго:

* тот же каталог сокетов, что у приёмника, **или** каталог из списка дефолтных
  при совпадении uid владельца;
* имя файла — `<pid>.sock`, либо `<pid>-<8 hex>.sock`, либо `<hex>.sock`;
* симлинк в качестве адреса отвергают.

Не прошедший проверку адрес ошибки не даёт — ответ просто не отправляют.

### Квитанции

```json
{"type":"control","action":"peer_message_status",
 "orig_msg_id":"<msg_id сообщения>","status":"held|denied|expired|delivered|dropped"}
```

`dropped` дополнительно несёт `drop_reason` (например `queue-full`) и
`dropped_msg_ids`.

Контракт снят с бинаря **2.1.302** (встроенный JS и owned-прогоны
`mop dev inbox-probe`) и привязан к версии: при смене native его надо
перепроверить, молчание и idle на новой версии могут означать другое.

`peer_message_status` — канал удержания, отказа и дропа, а не подтверждения
приёма. Словарь статусов: `held | denied | expired | delivered | dropped`;
отказ идёт по проводу как `expired` с `status_detail:"refused"`. Статуса
`queued` или `accepted` не существует.

* Обычное сообщение, которое gate принимает, **не порождает квитанции**:
  кадр кладётся в очередь, отправителю не пишется ничего. Поэтому `unknown`
  после окна ожидания — правдивый терминальный исход, а не сбой.
* `delivered` означает «ранее удержанное сообщение освобождено» (одобрение
  в UI или снятие политики), и только после ingress guard. Обычная доставка
  его не получает. Это единственный положительный сигнал native.
* `denied | expired | refused | dropped` — явный отказ. Тихо теряются и
  другие пути: непустая строка обязательна, несовпавший `session_id`,
  `session.receive`-хук, съевший сообщение, поздний `dropped_by_hook`,
  неаутентифицированная или слишком длинная строка соединения — всё это
  пишет в лог и молчит. Отсюда правило: тишина не различает приём и потерю.
* `dropped` для каждой пары (отправитель, причина) приходит сразу только
  первый раз за 60 с; следующие схлопываются и уходят через 5000 мс, то есть
  могут опоздать к окну ожидания в 2 с. Исход тогда остаётся `unknown`,
  что безопасно.
* На bypass-получателе обычный текст без конверта уезжает в `held` и ждёт
  человека; поздний `delivered` после окна игнорируется. Заявлять
  `from-mode="bypass"` ради удержания нельзя — это ложная заявка о режиме.

Следствие для `notify_when_idle`: idle-квитанция моделируется только для
доставки в состоянии `accepted` с `notify_when_idle`
(`mop/server/sessions/endpoint_models.py`, `DeliveryReceipt.save`).
Обычная native-доставка остаётся `unknown`, поэтому подписка
`notify_when_idle` для неё **никогда не срабатывает**: notice не с чем
сопоставить. Idle — отдельное наблюдение, и в текущей модели для обычной
доставки его нет.

Вердикт `mop.client.local_bridge` следует этому контракту: `delivered` →
`accepted`; `denied|expired|refused|dropped` → `unavailable`; `held`,
неизвестные статусы и тишина → `unknown`. `unknown` терминален и никогда не
переотправляется; слитый write, idle, активность провайдера или UI исход не
повышают.

### «Сессия освободилась»

Подписка:

```json
{"msgV":1,"msg_id":"<uuid4 подписки>","type":"control",
 "action":"notify_when_idle","from":"uds:…","from_mode":"bypass"}
```

Ответ, когда сессия дойдёт до простоя:

```json
{"type":"control","action":"peer_idle_notice",
 "orig_msg_id":"<uuid4 подписки>","state":"idle",
 "from":"uds:…","from_mode":"bypass","msgV":1,"msg_id":"…"}
```

`orig_msg_id` — идентификатор подписки, а не сообщения. Требует auth-кадра.
Подписка одноразовая: notice приходит один раз и снимает её.

Прочие control-действия (`rename`, `yield_artifact_replies`,
`unyield_artifact_replies`) прочитаны в бинаре, в деле не используются.

## Что проверено, а что нет

Проверено на живой сессии: доставка кадра `type:"user"` и ответ модели;
удержание в held без конверта и автодоставка с `from-mode="bypass"`;
`notify_when_idle` → `peer_idle_notice` (и тишина без auth-кадра);
переменные окружения у дочернего процесса. Отдельно, на 2.1.302:
`peer_message_status` доходит до LocalBridge-подобного callback (отказ),
обычный принятый кадр не даёт квитанции, а контроль с чужим `session_id`
даёт тот же видимый из bridge trace, что и принятое сообщение, — поэтому
тишина не доказывает ни приём, ни потерю. Не проверялось:
`file_attachments`, `hop-chain`, `session_id`, поведение под
`crossSessionInbound: "refuse"`, windows-ветка; положительный
`held`/`delivered` контроль (нужен человек или смена настроек).
