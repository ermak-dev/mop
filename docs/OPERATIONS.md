# OPERATIONS: исполнитель веб-операций

Клик по дашборду (#461) — это операция над папетом: рестарт, обновление,
завод. Исполняет её воркер (`mop/server/opworker.py`, #476) — не фоновый
subprocess командлета и не привилегированный RPC, а тонкий слой приёма
поверх устойчивого журнала, зовущий библиотечный workflow
(`mop/common/ops.py`, #458) под инвариантом безопасности
(`ops.safety`, #460).

## Устойчивость

Журнал — `~/.config/mop/operations/ops.jsonl`, append-only со `fsync` на
каждой записи; payload исполнителя (workspace, message — чужие секреты)
живёт отдельным файлом `payload/<id>.json` со своим, коротким сроком и из
ответов GET не выходит. Хранилище недоступно — операция не запускается
вовсе: тихо продолжить без записи — потерять результат.

## Приём: транзакционная дедупликация

Intent пишется ДО эффекта и несёт actor, ключ идемпотентности и хэш
нормализованного запроса. Тот же actor с тем же ключом и тем же хэшем —
та же операция (двойной клик не запускает дважды); тот же ключ с другим
payload — отказ. Роль проверяется до первого эффекта: понижение отменяет
ещё не начатое; начатое доводится до этапа и аудируется.

## Модель

    queued → running → succeeded | refused | failed | partial

Перезапуск службы помечает незавершённую running-запись `unknown` —
без переигрывания эффектов; решение за админом по карточке папета
(#462). `unknown` запрещает автоматический повтор и не означает
`failed`: эффекта могли и быть, и не быть. `partial` — эффект был,
наблюдение не сошлось (карта исходов #458: accepted → partial,
registered → succeeded).

## Наблюдение рестарта (#464)

Рестарт воркер исполняет наблюдаемым режимом общей операции
(`ops.restart(..., observe=True)`): эффект RPC не считается успехом сам
по себе. Снимок сводки задачи (read-глагол `alloc`, едет с #126) пишется
в журнал (`baseline`) ДО RPC эффекта, затем тот же read-глагол опрашивается,
пока счётчик рестартов не сдвинется или задача не выйдет из running.
Прежний running — не успех: это та же старая сессия. Смена allocation ID
подтверждением не служит (рестарт задачи, а не новая аллокация) —
`unknown`. Увиденный рестарт с вернувшейся падшей задачей — `partial`
с причиной; увиденный без вернувшегося running за срок (`OBSERVE_WAIT`)
— `partial`; снова running — `succeeded`. Наблюдение только читает:
конкурентный send ничего не наблюдает.

Подъём службы донаблюдает прерванное наблюдение read-only тем же
сигналом (`ops.observe_restart` по журнальной `baseline`) — эффект не
переигрывается никогда. Сошлось — честный исход; не сошлось, нет базы
или нет транспорта — `unknown` с причиной. Транспорт восстановления
воркеру даёт поднимающая служба; читать он может, писать — нет.

## Сериализация

Конфликтующие действия сериализуются по устойчивой идентичности цели
(имя папета): пока по цели идёт незавершённая операция, следующая по той
же цели остаётся `queued` и доводится, когда цель освобождается. Другая
цель не ждёт.

## Сроки и очистка

Записи живут `RETENTION_DAYS` (30), payload — `PAYLOAD_DAYS` (3),
лимит незавершённых — `QUEUE_LIMIT` (100): всё — атрибуты воркера.
После очистки ключ уходит в tombstone — строку журнала без содержания:
тот же ключ после очистки — отказ («this key was purged»), а не молчаливая
новая операция. Дедупликация не обещана навсегда; tombstone держит её
границу честной.

## Аудит

Каждая операция пишет `ops.record` (#476): принципал HTTP и
сервис-отправитель — отдельные поля, payload сообщения не хранится.
Чтение результатов — только актуальная admin-роль; actor-supplied ID
чужой операции права чтения не даёт.

## HTTP-адаптер (#461)

`mop/server/adminapi.py` — вход клика в этот слой, и только он: гейты,
узкая схема, реестр операций, постановка в очередь, ответы. Workflow и
здесь не исполняется — ни в потоке запроса, ни где-либо ещё: POST
возвращает `202 accepted` с id операции, результат читается отдельным
GET (admin-only, без payload, no-store — в публичный SSE не попадает).

Гейты — по убыванию цены ошибки: роль (admin на каждом POST и GET;
гость — 401, вошедший не-admin — 403; роль перечитывается на каждом
запросе, упавший провайдер — закрыто, без сырой ошибки), Origin (POST
без Origin или с чужим — 403: браузер обязан слать, отсутствие — не
браузер), тело (строго `application/json`, ограниченная Content-Length,
JSON-объект без неизвестных полей). Схема — `{action, target, params}`:
никаких произвольных RPC subject/verb, shell/argv/env — лишние поля
режутся на разборе.

Коды различимы: 202 — только принятие, 409 — конфликт (другой payload
на цель с незавершённой операцией; повтор того же payload — тот же id),
4xx — валидация, 503 — транспорт и полная очередь. Детали ошибок —
allowlist-фразы (`sanitize`), не raw exceptions: в них ходят пути и
секреты.

Реестр операций — общая точка стыковки: воркер и операции
подключаются `Operations.register(action, params)`, HTTP-whitelist
может быть у́же CLI, но копии алгоритма не держит. Незарегистрированная
операция — 404 unsupported: кнопки в GUI нет, пока операция не
подключена. Send первого выпуска — только адресная доставка папету;
текст сообщения живёт в приватной задаче очереди с ограниченным сроком.
