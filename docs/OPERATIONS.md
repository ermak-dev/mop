# OPERATIONS: исполнитель веб-операций

Клик по дашборду (#461) — это операция над папетом: рестарт, обновнение,
завод. Исполняет её воркер (`mop/server/opworker.py`, #499) — не фоновый
subprocess командлета и не привилегированный RPC, а тонкий исполнитель
над библиотечным workflow (`mop/common/ops.py`, #458) под инвариантом
безопасности (`ops.safety`, #460). Своей очереди, замка цели и журнала у
воркера нет (#497: вторая копия «жизни операции» разошлась с реальностью —
вечный accepted, 409 часами): `Worker.run(verb, target, params, login)`
синхронно возвращает вердикт, поток операции даёт адаптер, тем же
транспортом, что CLI. Правда об исходе — аудит пула (`ops.record` →
`/api/journal`), как у CLI.

## Приём: идемпотентность в памяти

Приём держит адаптер (`mop/server/adminapi.py`): тот же payload, пока
операция жива, — тот же id (двойной клик не запускает дважды); другой
payload на ту же цель — вторая операция, она ждёт семафор цели, а не
отказывает. Завершённая операция ключ и цель освобождает: явный повтор —
новая операция, дедуп — про живой клик, не про историю. Память и есть
срок: рестарт службы честно читает незнакомый id как `unknown` со
ссылкой на журнал — дюрабельности «клик → вердикт» через рестарт нет
(осознанная граница #499). Роль проверяется до первого эффекта:
понижение отменяет ещё не начатое; начатое доводится до конца и
аудируется.

## Модель

    waiting → running → succeeded | refused | failed | partial | unknown

Семафор на устойчивую идентичность цели (имя папета; у add — origin):
операции одной цели едут по очереди, разных — параллельно. Семафор
освобождается в `finally`: зависший эффект (#497 — таймаут отдельным
слоем) не запирает цель навсегда и не требует переделки этого слоя.
`unknown` не означает `failed`: эффекта могли и быть, и не быть;
автоповтора нет, решение за админом. `partial` — эффект был, наблюдение
не сошлось (карта исходов #458: accepted → partial, registered →
succeeded; одна точка карты — `opworker.status_of`, для вердиктов обоих
видов).

## Наблюдение рестарта (#464)

Рестарт воркер исполняет наблюдаемым режимом общей операции
(`ops.restart(..., observe=True)`): эффект RPC не считается успехом сам
по себе. Снимок сводки задачи (read-глагол `alloc`, едет с #126)
операция берёт сама ДО RPC эффекта, затем тот же read-глагол
опрашивается, пока счётчик рестартов не сдвинется или задача не выйдет
из running. Прежний running — не успех: это та же старая сессия. Смена
allocation ID подтверждением не служит (рестарт задачи, а не новая
аллокация) — `unknown`. Увиденный рестарт с вернувшейся падшей задачей —
`partial` с причиной; увиденный без вернувшегося running за срок
(`OBSERVE_WAIT`) — `partial`; снова running — `succeeded`. Наблюдение
только читает: конкурентный send ничего не наблюдает. Прерванное
сервисом наблюдение не донаблюдает: вердикт читается `unknown` по
журналу — эффект не переигрывается никогда.

## Вердикт и SSE

Терминальный статус публикуется кадром `operation` в существующий поток
`/events` (#424): `{id, action, target, status, error?}`, причина —
закрытая фраза (`result_error`), payload в кадре нет. Тем же ходом
исход уезжает аудитом на шину (`ops.record` через `bus.emit` в субъект
events) — подписчик журнала получает его без перечитывания страницы.

## Аудит

Каждая операция пишет `ops.record` (#476): принципал HTTP и
сервис-отправитель — отдельные поля, payload сообщения не хранится и в
ответы не попадает. Чтение результатов — только актуальная admin-роль.

## HTTP-адаптер (#461)

`mop/server/adminapi.py` — вход клика в этот слой, и только он: гейты,
узкая схема, реестр операций, приём и статусы. Workflow и здесь не
исполняется в потоке запроса: POST возвращает `202 accepted` с id
операции, исполнение — поток на операцию (`mop-web-op-<id>`), результат
читается отдельным GET (admin-only, без payload, no-store).

Гейты — по убыванию цены ошибки: роль (admin на каждом POST и GET;
гость — 401, вошедший не-admin — 403; роль перечитывается на каждом
запросе, упавший провайдер — закрыто, без сырой ошибки), Origin (POST
без Origin или с чужим — 403: браузер обязан слать, отсутствие — не
браузер), тело (строго `application/json`, ограниченная Content-Length,
JSON-объект без неизвестных полей). Схема — `{action, target, params}`:
никаких произвольных RPC subject/verb, shell/argv/env — лишние поля
режутся на разборе.

Коды различимы: 202 — только принятие, 4xx — валидация и роль, 503 —
транспорт и неподключённый исполнитель. Конфликта 409 больше нет:
вторая операция на занятую цель принимается и ждёт (#497). Детали
ошибок — allowlist-фразы (`sanitize`), не raw exceptions: в них ходят
пути и секреты.

Реестр операций — общая точка стыковки: воркер и операции
подключаются `Operations.register(action, params)`, HTTP-whitelist
может быть у́же CLI, но копии алгоритма не держит. Незарегистрированная
операция — 404 unsupported: кнопки в GUI нет, пока операция не
подключена. Send первого выпуска — только адресная доставка папету;
текст сообщения живёт только в живой операции памяти.

## Завод и перевод через веб (#470)

Add и update едут через тот же слой: адаптер принимает клик, воркер
зовёт общие `ops.add`/`ops.update` (#458) — копии workflow нет.

Источником workspace служит ЯВНЫЙ удалённый источник: текст
`.mop/bootstrap.yaml` выкачивается из origin (`manifest.fetch`, дефолт
`remote_workspace`; подменяется проверками), происхождение — тем же
видом, что собирал командлет (#334), source всегда `origin`. Ни cwd, ни
локальных файлов сервера веб не читает: у страницы рабочей копии нет.

Заводить можно только заведённое: origin add обязан быть в реестре
сервера — иначе отказ до эффекта; реестр не подключён — отказ тоже
(fail closed). Цели у add нет (имя присвоит сервис), устойчивая
идентичность операции — сам origin: повторы одного origin ждут друг
друга, другие origin'ы не ждут; присвоенное имя едет фактом вердикта.

Update принимает `fresh` только явным bool — молчаливого режима нет:
keep (fresh false, origin прежний), replace (fresh true, origin прежний,
клон и разговор начнутся заново), remove (fresh true + новый origin,
пересадка). Спека читается один раз до эффекта — её origin решает, чей
workspace качать; force веб не даёт: чужая аренда — отказ (`ops.safety`,
#460), работа в клоне и unknown-факты — отказ до транспорта.

Payload (текст bootstrap'а) в вердикте, GET, SSE-кадре и аудит-записи
не живёт: он едет только в вызов операции.

## Смена модели через веб (#468)

`action: "model"` едет тем же ходом: приём адаптера принимает клик
(`params: {model}` — одна строка; кривой id превращается в `refused`
исполнением, а не в отказ HTTP — invalid-модель не ошибка запроса, а
исход эффекта), воркер зовёт общую `ops.switch_model` (#468) — второй
реализации нет, CLI/MCP и GUI исполняют один код.

Каталог для формы — не список страницы: GET `/api/admin/models`
(admin-only, no-store) читает живой `/v1/models` прокси клиентским ключом
установки (`catalog_read`, #391); ключ и адрес в ответе не живут — только
id. Лежащий прокси — общая фраза 503, без сырой ошибки. Парсер каталога
один (`llm.catalog_ids`): его же переэкспортирует клиентский
`models.ids` — CLI и сервер читают ответ прокси одним кодом.

Подтверждение — телеметрия, не «диалог закрылся»: до эффекта снимок
(`sessionId`, `model`, `model_at` из записей хуков #453), после — опрос,
пока та же сессия не покажет нормализованно ту же модель по свежей записи.
Свежий снимок «уже выбранной» — no-op `succeeded` без нажатий; устаревший —
эффект как заказан; отказ эффекта (диалог не закрылся, чужая аренда) —
`refused` с причиной; другая модель при живой сессии — `partial`;
тишина записи за срок — `unknown` (эффект мог и быть). Модель
не-disruptive: сессия переживает смену, `ops.safety` её не отклоняет.
Опрос ведут часы и сон воркера: застрявший тестовый штамп не усыпляет
наблюдение по-настоящему.

Слэш-команда `/model` (CLI/MCP `type`) остаётся ручным ходом: TUI
исполняет её сам, а «диалог закрылся» — не подтверждение. Веб-ход даёт
привязку к сессии и свежую запись модели — того, чего слэшу взять неоткуда.
