# Драйвер узла: в чём живёт папет

**Это план работ, а не описание существующего.** Ничего из перечисленного в
репозитории ещё нет; порядок этапов — в конце.

Nomad решает, ГДЕ стоит папет, шина ([BUS.md](BUS.md)) — КАК с ним говорить.
Третий вопрос сегодня не задан, потому что ответ всегда один: папет живёт в
`$HOME` узла, общем со всеми соседями — клон в `~/puppets/<имя>`, tmux-сокет в
`/tmp/tmux-<uid>`, файл сессии в `~/.claude/sessions`, транскрипты в
`~/.claude/projects`. Изоляции между папетами одного узла нет никакой.

Драйвер отвечает на третий вопрос: **В ЧЁМ живёт папет**.

## Два определения

**Узел** переопределять не нужно, оно уже есть и работает: имя в инвентаре =
имя клиента Nomad = имя в субъекте шины. Новое у узла ровно одно — он знает,
каким драйвером делает тела.

**Тело** — то, что зовётся именем папета и в чём можно выполнить команду. Имя
тела — `pu-<проект>-<n>`, то же самое, что у джоба, клона и tmux-сервера.
VMID Proxmox в модель mop НЕ входит: это деталь драйвера, выводимая из
hostname. Второе имя для того же означало бы второе место, отвечающее на
вопрос «чей это папет», — ровно то, от чего предостерегает правило о шарде.

Абстракция ОДНА — драйвер узла; тело это то, что драйвер делает. У драйвера
`host` тело — сам узел (создание пустое, префикс команды пустой), и сегодняшняя
архитектура становится частным случаем, а не веткой, которую надо поддерживать
отдельно.

## Контракт

`mop/driver/` устроен как `mop/llm/`: один файл — один драйвер, имя файла —
имя драйвера, обнаружение глобом каталога, контракт проверяется громко при
загрузке. Половина узла импортирует только stdlib и `config`: тянуть на узел
`python-nomad` нельзя, агенту Nomad не нужен вовсе.

```python
# mop/driver/pve.py — "Proxmox: тело папета — контейнер LXC на узле-гипервизоре"

# ── жизненный цикл тела: зовёт bin/driver (из врапера), recycle, gc ──
def ensure(name, params)      # клон из шаблона шарда, лимиты, адрес, старт
def destroy(name)             # снос тела
def bodies() -> [name]        # что есть на этом узле — ростер без Nomad
def capacity() -> {...}       # память и место хранилища тел

# ── доступ в тело: зовут глаголы агента ──
def argv(name) -> [...]       # префикс команды: [] у host, ssh у контейнера
def push(name, path, data)    # положить файл внутрь (mop login)
def projects_dir(name)        # где транскрипты — mop stat, usage
def attach_argv(name)         # чем входит человек
def repair_argv(name)         # аварийный путь, когда основной молчит
```

Две половины в одном файле: узел и его тела — одно решение, а не два. Развести
их по двум реестрам значит получить решётку «узел × тело» и те же два места с
одним ответом.

## Кто выбирает драйвер

**Узел, а не папет.** Довод не вкусовой: Nomad выбирает узел УЖЕ ПОСЛЕ
регистрации спеки, а врапер лежит в спеке. Мастер в момент сборки спеки не
знает, на какой машине окажется папет, и заложить туда `pct exec` не может.

Источник правды — группа в инвентаре; `mop deploy` кладёт значение и в
`Environment=` юнита агента, и в `meta` клиента Nomad из одной переменной.
Агент драйвер из запроса НЕ берёт: иначе мастер шарда A прислал бы своё
значение и заставил агента исполнить команду не там.

## Врапер делится надвое

* **Внешний** — в спеке джоба, драйвер-агностичен:
  `exec $HOME/mop/bin/mop driver run "$PU_NAME"`. Дальше узел сам поднимает
  тело и запускает в нём внутренний.
* **Внутренний** — сегодняшний `puppets.WRAPPER`, едет в спеке базой-64 в
  переменной окружения. Base64 заодно снимает целый класс ловушек: hcl2 в
  него не заглядывает, и двойные доллары там больше не нужны.

Обе ловушки при этом остаются верными и разъезжаются по механизмам: правка
логики ТЕЛА доезжает прогоном `mop deploy`, правка логики СЕССИИ по-прежнему
требует перерегистрации джоба. Утащить внутренний врапер в пакет на узле —
значит поменять инвариант, записанный в CLAUDE.md как MUST, и поменять молча.

## Что меняется у узла

| Что | Сегодня | С телами |
|---|---|---|
| `deploy/node.yml` | ставит на узел git, tmux, jq, claude | раскол: узлу — Nomad, python, агент, драйвер; телу — всё остальное (`deploy/body.yml`) |
| память | cgroup задачи Nomad | задача больше не содержит папета: `MemoryMB` — только бухгалтерия слотов, потолок ставится ТЕЛУ из той же настройки |
| ёмкость | память узла | она же минус чужие жильцы гипервизора (`MOP_RESERVED_MB`, уже есть) |
| `disk` | `df $HOME` | хранилище тел; на этом числе стоит `mop gc`, менять молча нельзя |
| `pu-sweep` | клоны и target без tmux-сессии | плюс ярус «тело без живого джоба»; старые ярусы обязаны продолжать видеть старые каталоги |
| `v_local` | сокеты в `/tmp/tmux-*` | `bodies()` драйвера: на гипервизоре этот каталог пуст |
| `mop login` | два файла в `$HOME` узла | те же два файла в КАЖДОЕ тело узла через `push`; белый список путей тот же |
| креды шарда | раскатывает плейбук по узлам | плюс внутрь тела: шард известен в момент `ensure` |

## Доступ в тело на Proxmox

В REST API Proxmox **нет exec внутрь контейнера** (у VM есть guest-agent, у LXC
эквивалента нет) и нет записи файла. Значит жизненный цикл можно вести по API,
а работу с живым телом — нет.

Поэтому два пути, и оба названы:

* **основной** — ssh в тело: публичный ключ УЗЛА запекается в образ (приватный
  лежит на узле, у агента), адрес тела вычисляется из имени, ansible ходит
  обычным ssh с ControlPersist, а не медленным `proxmox_pct_remote`;
* **аварийный** — `pct exec` через root-обёртку на гипервизоре, которая сама
  проверяет, что hostname тела начинается с `pu-`. Нужен ровно тогда, когда
  основной не работает: у тела сломана сеть, sshd или права на `authorized_keys`.

**Ключ МАСТЕРА в образ не кладём.** Новой власти это не даёт (мастер и так
ходит ssh на узлы), но создаёт вторую дорогу к телу — мимо единственного места,
где проверяется шардирование. Агент сверяет шард субъекта с настоящим origin
клона; ssh о шардах не знает ничего.

## Образ и playbook

* **bake, основной** — `mop driver build <шард>` на управляющей машине:
  контейнер из базового образа → playbook → остановить → шаблон. Дальше каждое
  тело это клон шаблона (на zfs/lvm-thin — связанный, мгновенный). Падение
  playbook'а видно при сборке, а не в 3 часа ночи внутри врапера.
* **converge, отладочный** — `ensure` поднимает из базового образа и гоняет
  playbook на месте. Первый подъём долгий; нужен, пока playbook правится.

Публичный ключ попадает внутрь в момент создания (`ssh-public-keys` есть и у
`pct create`, и у POST `/nodes/{node}/lxc`), так что курица и яйцо не возникают.

Границу проекта playbook не нарушает: `deploy/body.yml` — то, чем обязано быть
ЛЮБОЕ тело (git, tmux, jq, claude, python3 + nats-py, пакет mop); тулчейн,
postgres и env-файлы остаются в `examples/` и подключаются настройкой.

## Ловушки

Каждая проявляется молча — поэтому список, а не «читай код».

* **Память перестаёт ограничиваться.** `pct exec` исполняется демоном, а не
  потомком задачи Nomad: лимиты задачи не ограничивают ничего, а арифметика
  слотов становится фикцией. Лимит обязан стоять на теле.
* **Смерть врапера обязана убивать сессию.** На «живой папет = живая
  tmux-сессия с именем джоба» стоит и ростер, и сбор сирот. Внешний врапер по
  TERM гасит сессию ВНУТРИ тела, а не умирает молча, оставив живого claude.
* **Пробу нельзя оставить на хосте.** Соблазн смонтировать наружу tmux-сокет и
  `~/.claude/sessions` ложный: `session.probe` проверяет живость через
  `os.kill(pid, 0)`, а pid тела в namespace хоста означает другой процесс или
  никакой — ломается различение `hung` и `offline`. Плюс tmux отказывается
  соединять клиента с сервером другой версии. Правило: всё про папета в теле
  исполняется В ТЕЛЕ; `session.py` для того и standalone.
* **`session.py` не хватает одного глагола.** CLI умеет `probe` и `send`, а
  подписка на простой (`_await_idle` для `send --notify`) живёт функцией внутри
  агента. Без формы `wait-idle <cwd> <timeout>` push-уведомления мастеру у
  контейнерных папетов молча не придут.
* **Папет может запереть агента снаружи.** Правкой `authorized_keys`,
  `sshd_config` или прав на `$HOME` (sshd со StrictModes). Лечение: папет в теле
  непривилегированный, `authorized_keys` в `/etc` под root.
* **Ключ хоста.** Пересозданное тело приезжает с новым ключом, и без
  `accept-new` плюс отдельного `known_hosts` агент после каждого рецикла
  читается как молчащий.
* **`/run/user/1000` внутри тела.** Без `loginctl enable-linger` каталог
  сокетов не появляется, и живые папета читаются мёртвыми — та же ловушка, что
  уже записана про юнит агента.

## Этапы

1. **Раскол плейбуков.** `deploy/node.yml` + `deploy/body.yml`, тело пока равно
   узлу. Проверяется на сегодняшнем пуле: два плейбука, поведение то же.
2. **Шов.** `mop/driver/` + `host.py`, все пробы агента через `argv()`, драйвер
   из инвентаря, `tests/driver.py` на контракт. Не меняется НИЧЕГО: `mop list`,
   `doctor`, `send`, `tail`, `attach`, `restart`, `recycle` на живом пуле плюс
   зелёный `tests/state.py`. Этап откатывается целиком.
3. **`pve.py`.** Nomad-клиент на гипервизоре, один папет в теле рядом с
   обычными узлами, весь список глаголов плюс `wipe`, `recycle`, `attach`.
4. **Периметр.** `disk`, `pu-sweep`, `gc`, `login`, `usage`, `mop driver build`.

Первые два этапа не обещают ничего нового и делаются до того, как гипервизор
вообще появится в инвентаре.

## Что останется непроверенным

Чистыми функциями проверяются контракт драйверов и матрица состояний. Всё
остальное — доставка сообщения, состояние папета, раскатка, лимиты памяти,
поведение при переезде аллокации — добывается только на живом пуле, и в отчёте
об этапе пишется, что именно прогнали, а что осталось непроверенным.
