# Драйвер узла: в чём живёт папет

**Все четыре этапа сделаны.** Драйверы `host` и `pve` работают, один папет
проекта `mop` живёт в контейнере LXC на узле `hyper`.

Nomad решает, где стоит папет, шина ([BUS.md](BUS.md)) — как с ним говорить.
Третий вопрос долго не задавали, потому что ответ всегда был один: папет живёт
в `$HOME` узла, общем со всеми соседями — клон в `~/puppets/<имя>`, tmux-сокет в
`/tmp/tmux-<uid>`, файл сессии в `~/.claude/sessions`, транскрипты в
`~/.claude/projects`. Изоляции между папетами одного узла нет никакой.

Драйвер отвечает на третий вопрос: **в чём живёт папет**.

## Два определения

**Узел** переопределять не нужно, оно уже есть и работает: имя в инвентаре =
имя клиента Nomad = имя в субъекте шины. Новое у узла ровно одно — он знает,
каким драйвером делает тела.

**Тело** — то, что зовётся именем папета и в чём можно выполнить команду. Имя
тела — `pu-<проект>-<n>`, то же самое, что у джоба, клона и tmux-сервера.
VMID Proxmox в модель mop не входит: это деталь драйвера, выводимая из
hostname. Второе имя для того же означало бы второе место, отвечающее на
вопрос «чей это папет», — ровно то, от чего предостерегает правило о проекте.

Абстракция одна — драйвер узла; тело это то, что драйвер делает. У драйвера
`host` тело — сам узел (создание пустое, префикс команды пустой), и сегодняшняя
архитектура становится частным случаем, а не веткой, которую надо поддерживать
отдельно.

## Контракт

`mop/driver/` устроен как `mop/common/llm/`: один файл — один драйвер, имя файла —
имя драйвера, обнаружение глобом каталога, контракт проверяется громко при
загрузке. Половина узла импортирует только stdlib и `config`: тянуть на узел
`python-nomad` нельзя, агенту Nomad не нужен вовсе.

```python
# mop/driver/pve.py — "Proxmox: тело папета — контейнер LXC на узле-гипервизоре"

# ── жизненный цикл тела: зовёт mop driver run (из врапера), recycle, gc ──
def ensure(name, params)      # клон из шаблона проекта, лимиты, адрес, старт
def destroy(name)             # снос тела
def bodies() -> [name]        # что есть на этом узле — ростер без Nomad
def capacity() -> {...}       # память и место хранилища тел

# ── доступ в тело: зовут глаголы агента ──
def argv(name) -> [...]       # префикс команды: [] у host, ssh у контейнера
def run_argv(name) -> [...]   # чем узел запускает врапер в теле
def push(name, path, data)    # положить файл внутрь (mop login)
def projects_dir(name)        # где транскрипты — mop stat, usage
def attach_argv(name)         # чем входит человек
def repair_argv(name)         # аварийный путь, когда основной молчит
def admit(name, let_in)       # впустить ключ сервера на время bootstrap'а (BOOTSTRAP.md)
def address(name)             # где сервер найдёт тело: у host — сам узел
async def templates()         # сборочные тела и образы; у host — []

IS_CONTAINER = True           # тела — отдельные объекты; False у host
SESSION_PY = "/…/session.py"  # путь к session.py внутри тела
```

Потребитель не ветвится по типу драйвера, а зовёт контракт (#151): флаг,
прочитанный вне `mop/driver/`, — это переключатель типа, и третий драйвер
проходил проверку контракта, чтобы упасть у потребителя. Всё, что потребители
берут у модуля, перечислено в `driver.CONSUMED`; `tests/driver.py` выводит этот
список из их кода и сверяет с каждым драйвером. Тип чужого узла по его meta —
`driver.is_container(driver.of_node(meta))`.

Две половины в одном файле: узел и его тела — одно решение, а не два. Развести
их по двум реестрам значит получить решётку «узел × тело» и те же два места с
одним ответом.

## Кто выбирает драйвер

**Узел, а не папет.** Довод не вкусовой: Nomad выбирает узел уже после
регистрации спеки, а врапер лежит в спеке. Мастер в момент сборки спеки не
знает, на какой машине окажется папет, и заложить туда `pct exec` не может.

Источник правды — группа в инвентаре; `mop server deploy` кладёт значение и в
`Environment=` юнита агента, и в `meta` клиента Nomad из одной переменной.
Агент драйвер из запроса не берёт: иначе мастер проекта A прислал бы своё
значение и заставил агента исполнить команду не там.

## Врапер делится надвое

* **Внешний** — в спеке джоба, драйвер-агностичен:
  `exec $HOME/mop/bin/mop driver run "$PU_NAME"`. Дальше узел сам поднимает
  тело и запускает в нём внутренний. Он же обязан по TERM гасить сессию внутри
  тела: pid сессии живёт в namespace тела, и убивать его снаружи нечего.
* **Внутренний** — сегодняшний `spec.WRAPPER`, едет в спеке базой-64 в
  переменной окружения. Base64 заодно снимает целый класс ловушек: hcl2 в
  него не заглядывает, и двойные доллары там больше не нужны.

Обе ловушки при этом остаются верными и разъезжаются по механизмам: правка
логики тела доезжает прогоном `mop server deploy`, правка логики сессии по-прежнему
требует перерегистрации джоба. Утащить внутренний врапер в пакет на узле —
значит поменять инвариант, записанный в CLAUDE.md как MUST, и поменять молча.

## Что меняется у узла

| Что | Сегодня | С телами |

| `pu-sweep` | клоны и target без tmux-сессии | плюс ярус «тело без живого джоба»; старые ярусы обязаны продолжать видеть старые каталоги |

## Доступ в тело на Proxmox

В REST API Proxmox **нет exec внутрь контейнера** (у VM есть guest-agent, у LXC
эквивалента нет) и нет записи файла. Значит работу с живым телом по API вести
нельзя, а жизненный цикл — можно.

Сделано **одной root-обёрткой** `deploy/mop-pve.j2` → `/usr/local/sbin/mop-pve`,
и цикл, и exec, и запись файла. Довод против «цикл по API, тело обёрткой»: это
два механизма, два набора прав и два места, отвечающих на вопрос «кто может
трогать тела». Обёртка узкая — набор глаголов закрыт ровно как у агента, и
каждый проверяет две вещи: VMID лежит в диапазоне mop и hostname контейнера
начинается с `pu-`. Пользователю пула выдан `sudo` на неё одну: `pct` целиком
был бы root на гипервизоре вместе с соседними боевыми контейнерами.

Внутрь живого тела — два пути, и оба названы:

* **основной** — ssh в тело: публичный ключ узла запекается в образ (приватный
  лежит на узле, у агента), адрес тела вычисляется из имени, ansible ходит
  обычным ssh с ControlPersist, а не медленным `proxmox_pct_remote`;
* **аварийный** — `mop-pve exec` (то есть `pct exec`) через ту же обёртку.
  Нужен ровно тогда, когда основной не работает: у тела сломана сеть, sshd или
  права на `authorized_keys`.

## Кто кого обслуживает

Узел объявляет в `meta.mop_projects`, чьих папетов умеет принять, и спека джоба
несёт ограничение по этому полю. У узла, где тело равно узлу, там `any`:
готовить ему нечего, и новый проект он подхватит без прогона `mop server deploy`. У
узла-гипервизора — перечень проектов, чьи образы на нём собраны; ведёт его
`mop driver build` динамической `meta` поверх строки из `client.hcl`.

Без этого планировщик ставил на гипервизор папета любого проекта, и тот висел
`pending` навсегда: врапер не находил шаблона и честно отказывался, но видно
это только в логе задачи на узле, а мастер проекта видел лишь «pending».
Поймано на живом пуле.

Регулярное выражение по списку, а не `set_contains`, потому что `any` обязано
быть словом целиком, а якоря — не украшение: без них `mop` совпадает с `mop2`,
а `op` с `mop`.

## Кто задаёт размеры тела

Осей две, и путать их дорого.

**Узел** отвечает за то, что свойство машины: драйвер, хранилище
(`mop_pve_storage` — на нём и тела, и образ проекта, который печёт
`pve-build.yml`, #227), мост и подсеть, диапазон VMID, резерв памяти под
чужих жильцов и потолки на тело.
Источник — инвентарь, строкой самого хоста; `mop server deploy` собирает эффективные
значения каждого узла в `~/.config/mop/node.env`, потому что `.env` на узлы не
едет. Список узловых настроек — `config.NODE_SCOPED`, одно место на систему.
Настройки процесса (`config.PROCESS_SCOPED`: `MOP_SERVER_DIR`, `MOP_BUS_CONFIG`, `MOP_PROJECT`) ставит родитель — `mop master`, врапер, юнит сборщика — и читаются они только из окружения: ни `.env`, ни `node.env` их не задают, в плейбуки они не едут.

В инвентаре машина объявляется один раз со всеми своими свойствами, а роли
(`server`, `master`, `puppet`) перечисляют только имена. Драйвер группой не
задаётся: группа под него существовала бы ради одной переменной, и ни один
плейбук на неё не смотрел бы — все смотрят на `mop_driver`.

Пример этой установки, и он же объясняет числа `hyper`. Из его 128 ГБ боевые
VM держат git 32 + win 16 + mirror 8 + builder 35 = 91 ГБ. Остаток отдан пулу
целиком — 40 ГБ, то есть пять тел по 8 ГБ, — и гипервизору остаётся около
восьми. Это работает потому, что память LXC — потолок, а не резерв: хост
тратит только занятое. Цена названа: упрутся все пять разом — хост уйдёт в OOM
и заберёт соседей, то есть боевые VM.

**Папет** отвечает за свою память (#197), и узел о ней говорит только
размещением — ниже, отдельным разделом.

**Проект** отвечает за размеры своего тела: память, диск, ядра. Источник —
файл `.mop` в корне самого проекта (`config.PROJECT_SCOPED`). Проект и есть
проект: значения лежат рядом с кодом, версионируются вместе с ним и
принадлежат тому, кто владеет проектом; центрального реестра, который
разойдётся с действительностью, при этом не заводится.

Порядок старшинства для диска и ядер: **узел > проект > установка >
дефолт**. Маленький гипервизор обязан уметь сказать «у меня столько не
бывает», и последнее слово за машиной — иначе `.mop` не настройка, а способ
занять гипервизор.

Диск и ядра читаются из `.mop` при сборке образа, на управляющей машине —
`git show HEAD:.mop` по зеркалу, которое сборка и так снимает. Дальше значения
живут в самом образе: `pct clone` копирует конфиг, тело наследует ядра и диск.
Поэтому на узел не едет ни одного из этих чисел.

### Память — свойство папета (#197)

Раньше у папета было три несвязанных числа: резерв Nomad
(`MOP_PUPPET_MEM_MB`) и потолок Nomad (`MOP_MEM_MB`) — только установки, а
настоящая память pve-тела — `pct --memory` образа, испечённая из `.mop` на
момент сборки. Слоты врали, большая просьба переподписывала гипервизор
незаметно, а на host-узле просьба проекта не действовала вовсе.

Теперь цепочка одна, `spec.memory`: **дефолт → `.env` → `.mop` проекта**.
Потолок — `MOP_MEM_MB` из `.mop`, иначе установки; резерв — бюджет установки
`MOP_PUPPET_MEM_MB`, но не выше потолка. Применяет её Nomad на обоих
драйверах: на host потолок — `MemoryMaxMB` задачи, то есть cgroup самого
claude; в pve-теле `pct` исполняется демоном, и потолок ставит телу `ensure`
глаголом `mop-pve memory` из переменной спеки `PU_MEM_MB` — на каждом
подъёме, до `start`, и новому клону, и стоящему телу. Ядра и диск остаются
образу.

Узел говорит о памяти одним: потолком `mop_body_mem_cap_mb`. `mop server deploy`
кладёт его в meta клиента Nomad (`mop_mem_cap_mb`), а спека требует
`${meta.mop_mem_cap_mb} >= потолок папета`. `>=` в Nomad 1.10 сравнивает
численно, только если обе стороны целые (`scheduler/feasible.go`,
`checkOrder`), иначе лексически — поэтому потолок узла обязан быть одним
целым числом мегабайт, и иное `mop server deploy` отвергает. Узел без ключа
ограничение не проходит: папет туда не встанет. Очередь из-за потолка
`mop doctor` называет отдельно от «нет образа» и «нет слотов».

Строки инвентаря `mop_mem_mb` больше нет: она не действовала нигде, и
`mop server deploy` отказывает, пока она стоит на любом хосте или в любой группе.

Спеку строит сервис кластера под учёткой пула, а `.mop` режет `mop server deploy`
на контроллере, поэтому просьбы доезжают до спеки файлом (см. CLUSTER.md) —
**со следующим прогоном `mop server deploy`**, не раньше. Проект, заведённый
`mop project add` между двумя прогонами, до следующего получает память
установки.

Две границы названы прямо:

* **`.mop` читается из origin, с дефолтной ветки.** Зеркало снимается
  целиком, а версия берётся его HEAD; так делают `mop server deploy` и сборка с
  аргументом. Исключение одно (#46): `mop driver build` без аргумента в
  рабочей копии берёт `.mop` из её файлов как лежат, без коммита и push —
  правку манифеста пробуют образом. Новой власти это не даёт: у того, кто
  собирает, и так ssh на узлы.
* **Состав образа проекту не отдан.** `MOP_BODY_EXTRA` называет файлы задач
  ansible, которые прогонятся на узле, и отдать их выбор чужому репозиторию
  значит отдать ему исполнение на гипервизоре. Базовый образ пока тоже не
  отдан: он меняет то, на что опирается `deploy/body-tasks.yml`, а добавить
  позже легко — отобрать обратно нет.

## Сеть тел

Отдельный мост `vmbr-mop` с NAT на самом узле, сеть — настройка
`MOP_PVE_SUBNET`. Не локалка, потому что адрес тела выводится из имени: такие
адреса, розданные в чужой локалке, однажды столкнутся с её DHCP. Шлюз —
производная настройка `MOP_PVE_GATEWAY`: тот же адрес нужен и драйверу, и
плейбуку, поднимающему мост, а вписанный дважды однажды разойдётся.

Цепочка одна: имя → VMID (sha1 имени в диапазоне) → адрес (сеть + VMID, номер
абсолютный: последние два октета адреса и есть VMID). Столкновение хешей
ловится громко в `ensure`, который сверяет hostname занятого номера с
ожидаемым.

Абсолютный номер, а не смещение от базы узла, — решение #58. База
(`MOP_PVE_VMID_BASE`) узловая, у второго гипервизора своя, и смещение от неё
сажало первое тело любого гипервизора на один и тот же адрес. От абсолютного
номера разные базы дают непересекающиеся куски одной плоской сети, и маршрут к
телам каждого гипервизора (`routes`) выходит однозначным сам собой. Правило
выдачи баз новым гипервизорам не вводится: пока гипервизор один, базу
назначает человек в инвентаре. Стоящее тело переутверждает свой адрес на
каждом подъёме (глагол `net`): переход после смены формулы, иначе тело со
старым адресом молчало бы до рецикла.

**Ключ мастера в образ не кладём.** Новой власти это не даёт (мастер и так
ходит ssh на узлы), но создаёт вторую дорогу к телу — мимо единственного места,
где проверяется проектирование. Агент сверяет проект субъекта с настоящим origin
клона; ssh о проектах не знает ничего.

**Сервер входит в тело только на время bootstrap'а** ([BOOTSTRAP.md](BOOTSTRAP.md)):
узел впускает его ключ глаголом `admit` и выпускает после ответа. В образе
ключа сервера нет по тому же доводу, что и ключа мастера.

**Сервер достаёт до тел напрямую — решение #59, записанное.** Тела за NAT
узла, но `FORWARD` пропускает в обе стороны, а `MASQUERADE` трогает только
исходящие: снаружи не хватало ровно маршрута. Каждый гипервизор называет
прогону свой адрес со стороны сервера и блоки своего куска сети (`routes_of`
— точное покрытие диапазона VMID, чтобы куски двух гипервизоров не налезали),
а сервер держит их юнитом `mop-routes` (`ip route replace`, переживает
перезагрузку при любом сетевом стеке). Маршрут даёт сеть, но не вход: в телах
`PasswordAuthentication no`, ключей в образе — только узла. Серверу дорога
нужна ради bootstrap'а песочниц и диагностики. Машина оператора маршрута не
получает: её настраивает `mop join`, а к телу она ходит через узел
(`mop attach`).

**Факты драйвера плейбукам — одной командой (#158).** Номер, имя и адрес
образа и сборочного тела, сеть с префиксом и шлюзом, маршруты, путь обёртки,
ключ узла и его known_hosts, верх диапазона VMID — всё это плейбуки (роль
`pve`, `deploy/pve-build.yml`) спрашивают у `mop server pve-facts --base N
[--project P --listing …]` на управляющей машине и читают из его JSON.
Считает `pve.facts()`; копий в jinja и `python3 -c` нет, список тел
разбирает один `parse_list`.

## Образ и playbook

В образ собирается и **зеркало репозитория проекта** (`~/.cache/mop-mirror/<проект>.git`),
а врапер клонирует с `--reference` на него: объекты берутся локально, всё, что
появилось в origin после сборки, git дотягивает сам. Клон остаётся полноценным
и свежим, а отставание зеркала лечится обычным `fetch`, не пересборкой. Снимают
зеркало на управляющей машине: ключа к git в сборочном теле нет, и заводить его
там незачем — приватный ключ узла приезжает в тело позже, при подъёме папета, а
в образе ему делать нечего, потому что образ живёт дольше любой ротации ключа.

`--dissociate` не ставится намеренно: он копирует объекты в клон и съедает весь
выигрыш. Цена названа — клон зависит от зеркала, и потому зеркало лежит в том же
теле и ровно столько же. Зеркала нет (драйвер `host`) — врапер клонирует как
раньше, и ветка эта обязана быть тихой.

* **bake, основной** — `mop driver build <проект>` на управляющей машине:
  сборочное тело → playbook → остановить → на место образа. Дальше каждое
  тело это клон образа (на zfs/lvm-thin — связанный, мгновенный). Падение
  playbook'а видно при сборке, а не в 3 часа ночи внутри врапера.
* **converge, отладочный** — `ensure` поднимает из базового образа и гоняет
  playbook на месте. Первый подъём долгий; нужен, пока playbook правится.

**Пересборка инкрементальна (#60).** Сборочное тело `pu-tmpl-<проект>-build` —
полная копия нынешнего образа, и playbook в нём играется идемпотентно:
качается только новое. Раньше сборка начиналась со сноса образа и тянула всё
заново (40–90 минут по каналу 22.09, четыре раза за день), а обрыв посередине
оставлял проект без образа; теперь старый образ стоит, пока новый не готов, и
подменяется полной копией сборочного тела в самом конце. Обрыв оставляет
сборочное тело под своим именем — следующий прогон той же команды продолжает
в нём. `--fresh` собирает из базового образа: инкремент не даёт чистоты, то,
чего в playbook'е уже нет, в образе остаётся, и диск тонкого тома не ужать.
Снятие флага шаблона (`pct set --template 0`) для этого не годится — флаг
снимается, но том остаётся базовым, read-only, и контейнер не стартует
(проверено на hyper 22.09).

Пересборка — операция над **проектом**, не над образом: у образа с живым клоном
не отнять место, поэтому `mop driver build` сначала останавливает папетов
проекта на контейнерных узлах и сносит их тела (`image.clear`), а после playbook'а
поднимает их той же спекой заново — при любом исходе, из нового образа или из
старого. Занятый папет — отказ до первого останова, `--force` снимает его; цена
названа: снос теряет прогретые `target`. Попутно закрыта ловушка «пересозданный
папет живёт на старом образе»: `ensure` переиспользует стоящее тело, а тел
после сборки не остаётся.

Публичный ключ попадает внутрь в момент создания (`ssh-public-keys` у
`pct create`), так что курица и яйцо не возникают.

**Ключ сборки.** Тело стоит за NAT узла, и управляющая машина достаёт до него
только через сам узел (`ProxyJump`). Значит на время сборки ей нужен свой ключ
— он кладётся рядом с ключом узла и снимается перед тем, как образ запечатан.
Постоянного ключа мастера в образе нет и не будет.

**Что узел переливает в тело на каждом подъёме** — закрытый список
`MOP_BODY_SEED` плюс креды проекта (их имя знает только `ensure`). Новых прав
телу это не даёт: у драйвера `host` папет живёт прямо в `$HOME` узла и все эти
файлы у него уже есть. Тело обязано быть тем же, чем был узел, — иначе первый
же `git clone` папета упирается в «Host key verification failed».

Границу проекта playbook не нарушает: `deploy/body.yml` — то, чем обязано быть
любое тело (git, tmux, jq, claude, python3 + nats-py, пакет mop); тулчейн и
postgres остаются в `sandbox.yaml` установки (её копия `sandbox.yaml.example` в
корне), пакеты проекта — в его `.mop/sandbox.yaml`; подключается всё
настройкой.

**Раскладка манифеста (#61).** Два файла в `.mop/` проекта, и имя говорит,
когда файл играется: `sandbox.yaml` — размеры тела и системные пакеты, печётся
в образ (на host-узле играется прогоном `mop server deploy`); `bootstrap.yaml` —
env-файлы и настройка окружения, играется при каждом старте песочницы. До #61
файлы звались `node.yaml` и `workspace.yaml` и обещали обратное тому, что
делал механизм: `workspace` пёкся в образ, `node` играл на машине-узле (на
гипервизоре — на самом Proxmox), а при старте не играло ничто. Старые имена
читаются переходно, оба как `sandbox`, с предупреждением в `mop server deploy` и
`mop driver build`; после переезда проектов чтение старых имён снимается.
Перекладка содержимого не косметика: `workspace.yaml` rugent ставил 697 МБ
пакетов за 183 с, и в bootstrap это платилось бы на каждом подъёме папета.

## Ловушки

Каждая проявляется молча — поэтому список, а не «читай код».

* **Память перестаёт ограничиваться.** `pct exec` исполняется демоном, а не
  потомком задачи Nomad: лимиты задачи не ограничивают ничего, а арифметика
  слотов становится фикцией. Лимит обязан стоять на теле — его ставит
  `ensure` из `PU_MEM_MB` спеки (#197); спека до #197 его не несёт, и тогда
  память тела остаётся образной.
* **Смерть врапера обязана убивать сессию.** На «живой папет = живая
  tmux-сессия с именем джоба» стоит и ростер, и сбор сирот. Внешний врапер по
  TERM гасит сессию внутри тела, а не умирает молча, оставив живого claude.
* **Пробу нельзя оставить на хосте.** Соблазн смонтировать наружу tmux-сокет и
  `~/.claude/sessions` ложный: `session.probe` проверяет живость через
  `os.kill(pid, 0)`, а pid тела в namespace хоста означает другой процесс или
  никакой — ломается различение `hung` и `offline`. Плюс tmux отказывается
  соединять клиента с сервером другой версии. Правило: всё про папета в теле
  исполняется в теле; `session.py` для того и standalone.
* **`session.py` не хватает одного глагола.** CLI умеет `probe` и `send`, а
  подписка на простой (`_await_idle` для `send --notify`) живёт функцией внутри
  агента. Без формы `wait-idle <cwd> <timeout>` push-уведомления мастеру у
  контейнерных папетов молча не придут.
* **Папет может запереть агента снаружи** — правкой `authorized_keys`,
  `sshd_config` или прав на `$HOME` (sshd со StrictModes). Помешать этому
  нечем: у пользователя пула в теле `sudo` без пароля, и он там нужен. Лечение
  не в запрете, а в аварийном пути: `mop-pve exec` идёт через `pct`, а не
  через ssh, и запертое тело им и открывают. `authorized_keys` в `/etc` под
  root — защита только от случайной правки своего `~/.ssh`, не от `sudo`.

  Границей служит сам контейнер, а не привилегии внутри него: он
  unprivileged, root в нём — обычный UID на хосте. Ровно поэтому привилегии
  внутри тела ничего не покупают ни папету, ни тому, кто его захватил, и
  отбирать их незачем.

  Вход root по ssh при этом закрыт: `pct create --ssh-public-keys` кладёт ключ
  узла и в `/root/.ssh/authorized_keys`, и глагол `keys` его оттуда убирает —
  драйвер ходит только под пользователем пула.
* **Ключ хоста.** Пересозданное тело приезжает с новым ключом, и без
  `accept-new` плюс отдельного `known_hosts` агент после каждого рецикла
  читается как молчащий.
* **`/run/user/1000` внутри тела.** Без `loginctl enable-linger` каталог
  сокетов не появляется, и живые папета читаются мёртвыми — та же ловушка, что
  уже записана про юнит агента.

Поймано при раскатке этапов 2–3, каждая — молча:

* **Драйвер узла обязан лежать файлом на узле**, а не строкой `Environment=` в
  юните агента. Спрашивают его двое с разным окружением: агент из своего юнита
  и внешний врапер из процесса задачи Nomad. Пока значение жило в юните, врапер
  его не видел и поднимал папета драйвером `host` — на гипервизоре это значит
  «прямо на гипервизоре, мимо тела», и выглядело как исправный подъём.
* **`$USER` в задаче Nomad — это root.** Клиент Nomad крутится под root и свой
  `$USER` отдаёт задаче, а дефолт `MOP_USER` брался оттуда. Драйвер собирал
  `ssh root@<тело>` и получал отказ по ключу при совершенно исправном ключе.
  Лечение: дефолт по uid процесса (`config.pool_user`), проверка в
  `tests/config.py`.
* **Двойные доллары врапера — замена, а не защита.** Они держались на том, что
  Nomad схлопывает `$$` в `$` перед запуском. В base64 схлопывать некому, и
  `$${p##*/}` доехало бы в тело буквально. Первый подъём контейнерного папета
  упал на «syntax error near unexpected token `(`».
* **sshd поднимается раньше своего конфига.** `apt-get install openssh-server`
  запускает его прямо из postinst, и `systemctl enable --now` на уже
  запущенном юните не делает ничего: sshd продолжает читать
  `~/.ssh/authorized_keys` вместо нашего пути под root. Выглядит как «ключ на
  месте, но не подходит». Лечение: `restart`, а не `--now`.
* **Штраф за источник у OpenSSH 10.** Несколько неудачных попыток — и sshd
  роняет соединения от этого адреса целиком, вместе с верным ключом. Адрес там
  ровно один: свой же узел. Лечение двойное — `IdentitiesOnly=yes` (не
  предъявлять телу каждый ключ из агента) и `PerSourcePenalties no` в теле.
* **`synchronize` теряет `ProxyJump`.** Модуль строит свой ssh сам и
  `ansible_ssh_common_args` при этом не берёт — честно идёт в сеть тел с
  управляющей машины, которой туда хода нет. Пакет едет архивом через
  `unarchive`, который идёт обычным соединением ansible.
* **Пересборка образа требует освободить связанные клоны.** Шаблон с живым
  клоном не сносится. С #60 тела проекта снимает сама сборка; что она не
  снимала — сироты без джоба — останавливает её громко, и это дело `mop sweep`.
* **Соединение врапера нельзя мультиплексировать.** Оно живёт столько же,
  сколько папет, и, повиснув клиентом на общем master'е, умирает вместе с ним,
  когда тот уходит по `ControlPersist`. ssh отдаёт 255, Nomad читает это как
  падение задачи и перезапускает здорового папета. Отсюда отдельный
  `run_argv` в контракте: пробы мультиплексируются, врапер — нет.
* **`mop mcp` в теле тянет весь пакет.** Без `python-nomad` узловой профиль
  MCP-сервера не стартует, claude показывает «1 failed», и папет остаётся
  живым, свободным и без инструментов.
* **Пакет в теле стареет вместе с образом.** Обещание «правка логики тела
  доезжает прогоном `mop server deploy`» держится только потому, что `ensure`
  дублирует пакет узла внутрь тела на каждом подъёме. Без этого в теле лежал бы
  пакет времён сборки образа: поймано на `mop stat` — у `usage.py` в теле ещё не
  было CLI, и расход контейнерного папета читался ровным нулём, неотличимо от
  «ничего не потратил».

## Этапы

1. ✅ **Раскол плейбуков.** `deploy/node.yml` + `deploy/body.yml`, тело пока равно
   узлу. Проверяется на сегодняшнем пуле: два плейбука, поведение то же.
2. ✅ **Шов.** `mop/driver/` + `host.py`, все пробы агента через `argv()`, драйвер
   из инвентаря, `tests/driver.py` на контракт. Не меняется ничего: `mop list`,
   `doctor`, `send`, `tail`, `attach`, `restart`, `recycle` на живом пуле плюс
   зелёный `tests/state.py`. Этап откатывается целиком.
3. ✅ **`pve.py`.** Nomad-клиент на гипервизоре, один папет в теле рядом с
   обычными узлами, весь список глаголов плюс `wipe`, `recycle`, `attach`.
4. ✅ **Периметр.** `disk` — ёмкость драйвера, не `df $HOME`; `pu-sweep` — ярус 0
   «тело без живого папета» (`mop driver sweep`), и на узле с телами ярусы 1–3
   не бегут: клонов в его `$HOME` нет; `login` — в узел и в каждое тело;
   `usage` — счёт внутри тела через CLI `usage.py`. (`mop driver build` уехал в
   этап 3: без образа проекта тела не из чего клонировать.)

Первые два этапа не обещают ничего нового и делаются до того, как гипервизор
вообще появится в инвентаре.

## Что останется непроверенным

Чистыми функциями проверяются контракт драйверов и матрица состояний. Всё
остальное — доставка сообщения, состояние папета, раскатка, лимиты памяти,
поведение при переезде аллокации — добывается только на живом пуле, и в отчёте
об этапе пишется, что именно прогнали, а что осталось непроверенным.
