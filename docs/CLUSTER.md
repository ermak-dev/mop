# Сервис кластера

Nomad за шиной: единственное на установке, что говорит с Nomad от чужого
имени. Код — `mop/server/cluster.py`, юнит `mop-cluster` на сервере (роль
`deploy/roles/cluster`), клиентская сторона — `bus.ask_cluster`.

## Зачем

Управление пулом было вторым интерфейсом рядом с шиной. Мастер ходил в Nomad
напрямую с management-токеном из `bootstrap.json`, и токен этот не знает про
проекты вовсе: имея его, мастер проекта снимал джоб любого другого. Шина
проекты делит кредами, Nomad не делит ничем, и `mop join` вёз токен каждому
оператору.

Теперь операция над пулом — глагол на шине. Токен живёт на сервере и больше
нигде, а оператору для работы с пулом нужен один порт (исключения названы в
[BUS.md](BUS.md)).

## Субъект

```
mop.<проект>.cluster.rpc.<логин>    глаголы проекта: свои папеты
mop.admin.cluster.rpc.<логин>       глаголы оператора: машины
mop.<проект>.cluster.rpc            без логина: машины (service -- дашборд, сборщик, #309) и переход (#207)
```

Свой субъект, а не `server.rpc` bootstrap'а, по одной причине: в субъект
сервера имеет право писать агент узла (`node-<узел>` в `nats-server.conf` —
узел просит bootstrap песочницы за папета). Положи туда глаголы над Nomad, и
джобы регистрирует и снимает любой узел. Новый субъект прав никому не
добавляет: у оператора проекта уже есть весь `mop.<проект>.>`, у папета и
узла его нет, и правки конфига NATS завод сервиса не потребовал.

## Глаголы

| Глагол | Кому | Что делает |
|---|---|---|
| `ping` | всем | жив ли сервис и видит ли он Nomad |
| `roster` | проекту | джобы папетов и их аллокации глазами проекта |
| `pool` | проекту | ёмкость узлов: свободно, всего, слоты |
| `add` | проекту | завести папета: `(origin)`; за воротами владения |
| `update` | проекту | перерегистрировать: репозиторий и история; стоящий папет остаётся на своём узле (#289), за воротами владения |
| `restart`, `stop` | проекту | аллокация папета; за воротами владения |
| `delete` | проекту | снять джоб (`purge=false` оставляет остановленным — так работает рецикл); за воротами владения |
| `alloc` | проекту | аллокация папета и драйвер её узла |
| `spec` | проекту | метаданные джоба и вердикт «спека устарела» |
| `nodes` | оператору | узлы: драйвер, состояние, ёмкость |
| `drain`, `up`, `forget` | оператору | жизненный цикл узла |
| `meta` | оператору | динамическая meta узла |
| `secret_put`, `secret_list`, `secret_remove` | проекту | секреты проекта: файлы и переменные (#127, [BOOTSTRAP.md](BOOTSTRAP.md)) |
| `bootstrap_result` | проекту | итог последнего прогона bootstrap'а папета: метка регистрации, коммит, ok/задача/сообщение (#334, docs/BOOTSTRAP.md) |
| `landing` | проекту | токен посадки: `take`/`give`/`show`, `(action, holder, puppet, force)` (#42) |
| `projects` | оператору | реестр проектов и их лимиты |
| `project_add` | оператору | завести проект: `(origin)` |
| `project_delete` | оператору | снять проект: `(name)`, отказ при живых папетах |
| `project_limit` | оператору | лимит папетов: `(name, value)` |
| `give_up` | оператору | остановить джоб, чей bootstrap сдался (#345): просит mop-bootstrap после ответа узлу, сервис перечитывает запись итога и останавливает (purge false) только сдавшийся текущий ключ ([BOOTSTRAP](BOOTSTRAP.md)) |

Узловые глаголы — оператору, как и `disk` на агенте: строка узла говорит,
чьи образы на нём собраны и кто его делит, а это не дело мастера проекта.
Ёмкость (`pool`) — другое: по свободным слотам мастер решает, заводить ли
папета, и видел он её всегда.

`roster` со `stale=true` добавляет вердикт об устаревшей спеке. Только по
просьбе: он стоит вызова API на каждый джоб, а нужен одному `mop server doctor` —
платить за него в каждом `mop list` значило бы платить за чужой глагол.

Кроме глаголов у сервиса свой поток (#391): на старте и раз в пять минут
раздача ключа LLM-прокси узлам (`mop/server/proxykey.py`,
[PROXY.md](PROXY.md)) — по отпечатку, молча, когда ключ не менялся.

## Проверка прав

Проект берётся из СУБЪЕКТА, первым токеном. Не из тела запроса: субъект
проверен правами NATS, тело пишет кто угодно. Дальше проект сверяется с
`Meta.origin` джоба — единственной правдой о том, чей это папет; имя
`pu-<проект>-<n>` собирается из того же basename, но именем не доказывается
ничего.

Три исхода, и они разные:

* джоба нет — не отказ прав, а отсутствие джоба, иначе опечатка в имени
  читается как «нет прав»;
* джоб есть, метки нет — отказ мастеру и разрешение оператору: чей
  непомеченный джоб, из него самого не узнать (так же `puppets.visible`
  показывает такие только оператору);
* метка чужая — отказ с именем настоящего владельца.

Завод и смена репозитория — в границах проекта: `add` с чужим origin и
`update` на чужой origin отвергаются. Иначе папет проекта клонировал бы чужой
репозиторий ключом пула, оставаясь на кредах своего проекта.

Матрица проверяется без кластера: `python3 tests/cluster.py`.

## Лимит папетов проекта

`add` сверх потолка проекта — отказ с числами: сколько живых джобов у
проекта и какой у него лимит (#107). Лимит — свойство проекта, а не человека:
сервис видит проект из субъекта, но не того, кто спрашивает. Считается он для
проекта из origin запроса, поэтому оператор через `mop.admin.*` упирается в
тот же потолок. Живые — джобы `pu-<проект>-*` не в статусе `dead`; уже
работающих сверх нового, пониженного лимита никто не снимает.

Лимиты правит `mop project limit <проект> <N|none>` с любой машины оператора
глаголом `project_limit` (`0` — заморозка); файл `~/.config/mop/limits.json`
лежит на сервере и пишет его только сервис (#117). Читает он его на каждый
`add`, рестарт не нужен.

Токен посадки (#42) — ровно один папет между merge и push на проект — тоже
у сервиса: у двух мастеров одного проекта он иначе жил бы в двух головах.
`take` — CAS под замком: свободен или уже у того же держателя для того же
папета — выдан, иначе отказ с держателем, папетом и временем; `give` —
только держателю; `force` забирает у ушедшего мастера и называет, у кого.
Истечения нет. Держатель — логин вызывающего из субъекта (#207, docs/BUS.md
«Кто просит»); на прежнем субъекте — названный телом. Файл
`~/.config/mop/landing.json` — сервиса, а не прогона: `mop server deploy` его не
кладёт, и рестарт сервиса токен не роняет. Клиент — `mop landing`.

## Забыть узел

`forget` отказывает дважды. Первый отказ -- по инвентарю (#178): узел, который
остался в `inventory.yaml` контроллера, следующий `mop server deploy` молча ставит
снова, поэтому сначала его убирают оттуда и прогоняют deploy. Инвентарь лежит в
рабочей копии контроллера (бывает, что в `/root`), а сервис работает под
учёткой пула и туда не ходит. Поэтому
`mop server deploy` шлёт плейбуку список хостов инвентаря (`ansible-inventory
--list`), роль `cluster` кладёт его в `~/.config/mop/inventory-hosts.json`,
и сервис читает этот файл на каждый `forget` -- до первого вызова Nomad. Если
файла нет (сервер развёрнут до #178), отказа по инвентарю нет. Второй
отказ -- `nomad.forget_refusal`: на узле ещё что-то живёт, или он открыт
планировщику.

## Проекты

Реестр проектов, лимиты и пароли `puppet-*` живут на сервере, и правит их
только сервис (#117): `mop project add|delete|limit|list` — клиенты шины под
ролью `admin`, контроллер для этого не нужен. Завод проекта — одна машина:
запись реестра, пароль проекта (`mop/server/natsconf.py` заводит недостающий и не
трогает имеющийся), файл пользователей шины `/etc/nats/users.conf` и SIGHUP
`nats-server` — он работает под тем же пользователем пула (#115).

`mop project add` делает проект готовым целиком (#124): регистрация на шине,
`.mop/bootstrap.yaml` на сервер глаголом `put`, образ — сборщиком (ниже), если
его нет хотя бы на одном контейнерном узле; `--update` и `--rebuild` собирают
и существующий. После этого `mop add` ставит папета сразу, ничего вручную.

SIGHUP о битом конфиге не сообщает, поэтому сервис после него подключается к
шине под новым `puppet-<проект>` и только тогда отвечает `ok`. Не пустила —
реестр и файл пользователей откатываются, и ответ — ошибка.

Писать файл пользователей шины значит решать, кто на ней и с какими правами.
Это даётся учётке пула на сервере сознательно: у неё уже есть токен Nomad,
то есть любой код на любом узле, и шина к этому ничего не добавляет.

## LLM

Провайдеров и профилей больше нет (#379): единственный сервер установки —
LLM-прокси на контроллере ([docs/PROXY.md](PROXY.md)). Ротация аккаунтов,
ротация моделей по квоте и refresh токенов живут внутри прокси; mop из
политики держит только `/model`-лечение доктора (`MOP_FALLBACK_MODEL`,
слово `opus` и др. обслуживают алиасы прокси).

## Спеку собирает сервер

Глагол — `add(origin)`, а не `register(spec)`. Приняв готовую спеку,
сервис отдал бы исполнение произвольного кода на узлах любому, кто дотянулся
до шины, и токен на сервере не защищал бы ничего: спека — это командная
строка задачи. Поэтому `spec.job_spec` зовётся здесь, а проситель называет
только origin и нужна ли история каталога.

Память папета — тоже решение сервиса (#197): `spec.memory` по цепочке
дефолт → `.env` → `.mop` проекта даёт резерв и потолок задачи, потолок едет в
окружение (`PU_MEM_MB`) и в ограничение размещения по meta узла
(`mop_mem_cap_mb`). `.mop` сервис не читает — он у контроллера, как и
инвентарь; `mop server deploy` уже режет манифесты всех проектов, и роль `cluster`
кладёт из них только просьбы в `~/.config/mop/project-asks.json`, `{проект:
{настройка: значение}}`. Сервис читает файл на каждую сборку спеки. Нет файла
или проекта в нём — память установки, без отказа; поэтому правка `.mop`
доходит до спеки со следующим прогоном deploy. Просьба, которую нельзя
применить (не целое число мегабайт), — отказ сборки спеки с именем папета.

## Сборка образа

Образ проекта собирает не сервис кластера, а соседний подписчик на сервере —
`mop-builder` (`mop/server/builder.py`, #123), глагол
`build(origin, mode[, node])` в `mop.admin.build.rpc`, только оператору;
`node` сужает сборку до одного контейнерного узла (#280,
[DRIVER.md](DRIVER.md)). Под пользователем контроллера: плейбук сборки идёт
его инвентарём и ключами к гипервизорам; на шину — как `service`
(`MOP_SERVER_DIR` указывает на каталог сервера пользователя пула).

Режимы: `missing` — собрать, только если образа нет хотя бы на одном
контейнерном узле; `update` — инкремент; `rebuild` — с базового образа. Ход —
потоком в инбокс просителя (`bus.ask_stream`): шаг (задача ansible, снос и
подъём тел, объявление образа), строки вывода ansible пачками (`lines`, не
чаще раза в 0,5 с, #140) и сердцебиение, итог — последним, при отказе с
хвостом вывода. `mop project add` показывает строки на терминале окном над
шагом и стирает его при успехе; `-v` печатает их все. Сборки идут по одной:
шаблоны делят зеркало (#100).

## Чего сервис не делает

* Не собирает состояние папета: факты даёт агент узла, вердикт — чистая
  функция у мастера ([BUS.md](BUS.md)).
* Не играет манифесты проектов: `.mop` проекта — слои узла и тела, это
  `mop server deploy` на контроллере.
* Не персистентен: запрос упавшему сервису не доедет, и это правильно —
  отложенная регистрация джоба через минуту после отказа хуже отказа.
  Отсутствие подписчика шина отдаёт сразу (`NoRespondersError`), а не
  таймаутом, поэтому «сервис не запущен» и «Nomad молчит» — разные ответы.
