# Сервис кластера

Nomad за шиной: единственное на установке, что говорит с Nomad от чужого
имени. Код — `mop/cluster.py`, юнит `mop-cluster` на сервере (роль
`deploy/roles/cluster`), клиентская сторона — `bus.ask_cluster`.

## Зачем

Управление пулом было вторым интерфейсом рядом с шиной. Мастер ходил в Nomad
напрямую с management-токеном из `bootstrap.json`, и токен этот не знает про
проекты вовсе: имея его, мастер проекта снимал джоб любого другого. Шина
проекты делит кредами, Nomad не делит ничем, и `mop join` вёз токен каждому
оператору.

Теперь операция над пулом — глагол на шине. Токен живёт на сервере и больше
нигде, а оператору для работы с пулом нужен один порт (исключения названы в
[BUS.md](BUS.md)).

## Субъект

```
mop.<проект>.cluster.rpc    глаголы проекта: свои папеты
mop.admin.cluster.rpc       глаголы оператора: машины
```

Свой субъект, а не `server.rpc` bootstrap'а, по одной причине: в субъект
сервера имеет право писать агент узла (`node-<узел>` в `nats-server.conf` —
узел просит bootstrap песочницы за папета). Положи туда глаголы над Nomad, и
джобы регистрирует и снимает любой узел. Новый субъект прав никому не
добавляет: у оператора проекта уже есть весь `mop.<проект>.>`, у папета и
узла его нет, и правки конфига NATS завод сервиса не потребовал.

## Глаголы

| Глагол | Кому | Что делает |
|---|---|---|
| `ping` | всем | жив ли сервис и видит ли он Nomad |
| `roster` | проекту | джобы папетов и их аллокации глазами проекта |
| `pool` | проекту | ёмкость узлов: свободно, всего, слоты |
| `add` | проекту | завести папета: `(origin, profile)` |
| `update` | проекту | перерегистрировать: репозиторий, профиль, история |
| `restart`, `stop` | проекту | аллокация папета |
| `delete` | проекту | снять джоб (`purge=false` оставляет остановленным — так работает рецикл) |
| `alloc` | проекту | аллокация папета и драйвер её узла |
| `spec` | проекту | метаданные джоба и вердикт «спека устарела» |
| `nodes` | оператору | узлы: драйвер, состояние, ёмкость |
| `drain`, `up`, `forget` | оператору | жизненный цикл узла |
| `meta` | оператору | динамическая meta узла |

Узловые глаголы — оператору, как и `disk` на агенте: строка узла говорит,
чьи образы на нём собраны и кто его делит, а это не дело мастера проекта.
Ёмкость (`pool`) — другое: по свободным слотам мастер решает, заводить ли
папета, и видел он её всегда.

`roster` со `stale=true` добавляет вердикт об устаревшей спеке. Только по
просьбе: он стоит вызова API на каждый джоб, а нужен одному `mop doctor` —
платить за него в каждом `mop list` значило бы платить за чужой глагол.

## Проверка прав

Проект берётся из СУБЪЕКТА, первым токеном. Не из тела запроса: субъект
проверен правами NATS, тело пишет кто угодно. Дальше проект сверяется с
`Meta.origin` джоба — единственной правдой о том, чей это папет; имя
`pu-<проект>-<n>` собирается из того же basename, но именем не доказывается
ничего.

Три исхода, и они разные:

* джоба нет — не отказ прав, а отсутствие джоба, иначе опечатка в имени
  читается как «нет прав»;
* джоб есть, метки нет — отказ мастеру и разрешение оператору: чей
  непомеченный джоб, из него самого не узнать (так же `puppets.visible`
  показывает такие только оператору);
* метка чужая — отказ с именем настоящего владельца.

Завод и смена репозитория — в границах проекта: `add` с чужим origin и
`update` на чужой origin отвергаются. Иначе папет проекта клонировал бы чужой
репозиторий ключом пула, оставаясь на кредах своего проекта.

Матрица проверяется без кластера: `python3 tests/cluster.py`.

## Лимит папетов проекта

`add` сверх потолка проекта — отказ с числами: сколько живых джобов у
проекта и какой у него лимит (#107). Лимит — свойство проекта, а не человека:
сервис видит проект из субъекта, но не того, кто спрашивает. Считается он для
проекта из origin запроса, поэтому оператор через `mop.admin.*` упирается в
тот же потолок. Живые — джобы `pu-<проект>-*` не в статусе `dead`; уже
работающих сверх нового, пониженного лимита никто не снимает.

Лимиты правит `mop project limit <проект> <N|none>` на контроллере
(`~/.config/mop/limits.json`, `0` — заморозка), на сервер их кладёт
`deploy/projects.yml` тем же файлом задач, что играет роль `cluster`. Сервис
читает файл на каждый `add`, рестарт не нужен.

## Спеку собирает сервер

Глагол — `add(origin, profile)`, а не `register(spec)`. Приняв готовую спеку,
сервис отдал бы исполнение произвольного кода на узлах любому, кто дотянулся
до шины, и токен на сервере не защищал бы ничего: спека — это командная
строка задачи. Поэтому `puppets.job_spec` зовётся здесь, а проситель называет
только origin, профиль и нужна ли история каталога.

## Чего сервис не делает

* Не собирает состояние папета: факты даёт агент узла, вердикт — чистая
  функция у мастера ([BUS.md](BUS.md)).
* Не заводит проектов: пользователи NATS — реестр проектов и прогон
  (`mop project`), то есть контроллер.
* Не персистентен: запрос упавшему сервису не доедет, и это правильно —
  отложенная регистрация джоба через минуту после отказа хуже отказа.
  Отсутствие подписчика шина отдаёт сразу (`NoRespondersError`), а не
  таймаутом, поэтому «сервис не запущен» и «Nomad молчит» — разные ответы.
