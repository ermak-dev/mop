# CRED: кредиты провайдеров LLM

Кредит — именованная авторизация у провайдера LLM (логин claude.ai, ключ
GLM), которую сервер выдаёт папетам. Эпик #281; здесь то, что уже
работает: логин claude без браузера на сервере (#282) и реестр кредитов с
пробой провайдеров (#283).

## Реестр

```
mop cred list                     # что держит сервер: статус, сброс, загрузка
mop cred status [имя]             # спросить провайдеров сейчас, та же таблица
mop cred add z1 --profile glm --key-file - --owner ivan@example.dev < key.txt
mop cred rm z1
```

Дом кредита на сервере: `~/.config/mop/creds/<имя>/`, 0700. Клиент `claude` при этом нужен на самом контроллере, для пользователя пула (PATH юнита или `~/.local/bin`): его ставит `mop server deploy` (#293), а без него логин, продление токена и `auth status` отказывают словами «claude is not installed on the server», не трассой (#292). Рядом с
секретом лежит `cred.json`: `name`, `profile`, `kind`, `owner`,
`added_at`, `status`. Секрет — по виду кредита:

| kind | что лежит | откуда |
|---|---|---|
| `login` | `.claude/.credentials.json` (дом клиента claude) | `mop cred login` |
| `token` | файл `token`, токен на год | `mop cred login --setup-token` |
| `key` | файл `key`, ключ API провайдера | `mop cred add` |

Секрет наружу не выходит: `cred_add` везёт ключ по шине внутрь один раз, а
списки и страница дашборда читают запись без него. Владелец — почта: для
логина claude её сообщает `claude auth status`, для ключа — `--owner`.

### Три статуса

Проба — хук `probe` профиля (`mop/common/llm/<профиль>.py`): у GLM ручка
`quota/limit` самим ключом, у claude — `api/oauth/usage` access-токеном
дома (нужна область `user:profile`, её даёт `auth login`; `setup-token`
получает 403 без области, и это читается как «активен, статус
неизвестен», а не как мёртвый кредит). Ответ ложится в `cred.json` с
временем пробы; `mop cred list` показывает:

| статус | значит | откуда |
|---|---|---|
| `active` | можно выдавать | проба прошла, окна не исчерпаны |
| `quota wait` | ждёт квоты до сброса (`resets`) | окно на 100 % у claude, `remaining 0` у GLM |
| `needs login` | ждёт ручной авторизации | 401/403, ключ отозван, нет секрета |
| `unknown` | пробы ещё не было | |

### Продление токена

Токен логина claude живёт часы и обновляется самим клиентом при запросе.
Сервер за два часа до истечения (`credreg.needs_keepalive`) зовёт
`claude -p "reply with one word: ok" --model haiku` в доме кредита: один
копеечный запрос, и `.credentials.json` переписан. Обмен и client id
остаются внутри клиента. Токен `setup-token` и ключи не продлеваются.

## Дом кредита

`~/.config/mop/creds/<имя>/` на сервере, 0700. Для claude это `HOME`
клиента: логин кладёт туда `.claude/.credentials.json`, а флаги первого
запуска (`.claude.json`: онбординг пройден, вопрос о восстановлении
длинного разговора снят) пишутся те же, что врапер папета, — чтобы
`claude -p` в этом доме не встал на экране, где нажать некому. Токен
`setup-token` лежит рядом файлом `token`, 0600.

## Аренда: какой кредит держит папет

Папет держит аренду одного кредита: имя лежит в мете джоба (`Meta.cred`)
и едет через перерегистрацию как ветка мастера. `mop add --cred имя` и
`mop update --cred имя` назначают явно; сервис кластера отказывает, если
такого кредита нет или он другого профиля. Без `--cred` сервер выбирает
первый по имени активный кредит профиля, а если активных нет — папет живёт
без аренды, логином оператора из `mop login`, как прежде. `mop cred list`
показывает держателей колонкой `holders`.

Что уезжает в тело (глагол `write` агенту узла, белый список путей):

| Вид | Файлы в теле |
|---|---|
| `login` | `.claude/.credentials.json` без `refreshToken` и метка `.local/state/mop/cred` с именем кредита |
| `key` | строка `KEY=…` в `.config/mop/secrets.env` и та же метка |
| `token` | пока не раздаётся: нужен окружением при старте claude |

Refresh-токен остаётся в доме кредита на сервере: обновляет его один
сервер, тела не обновляют ничего, и ротация провайдером им не страшна.
Ограничение этого шага: `write` кладёт файлы в узел и во все его живые тела,
так что два кредита одного профиля на одном узле не уживутся — адресная
запись в одно тело остаётся следующим шагом.

`mop login` теперь ещё и сдаёт логин оператора в реестр кредитом под именем
логина на шине: папеты с арендой на него получают свежий файл от сервера,
остальные — прежней раздачей.

## Приписывание провалов и цикл сервиса

Хук `session.py hook` вписывает имя кредита из метки в запись хода. Раз в
пять минут поток сервиса кластера обходит реестр: снимает брошенные логины
по TTL, продлевает токены домов логинов (`claude -p`), пробует провайдеров,
раздаёт держателям то, что изменилось с прошлой раздачи (отпечаток —
`pushed.sha` в `cred.json`), и читает записи ходов держателей глаголом
`states`. Провал `authentication_failed` делает кредит `needs_login`, если
дом не менялся после хода, иначе просто раздаёт свежее; `rate_limit` — `ждёт
квоты` до времени из текста провала (пояс в тексте не назван, читается как
UTC); `billing_error` — `ждёт квоты` без времени. Каждое действие — строка
в журнале `mop-cluster`.

## Логин без браузера: клиент в pty

```
mop cred login anton              # claude auth login: полный набор областей
mop cred login anton --setup-token  # claude setup-token: токен на год, только inference
```

OAuth не переизобретается: client id, PKCE и адреса живут внутри
официального клиента, сервер только ведёт с ним диалог
(`mop/server/credlogin.py`). Клиент без браузера печатает адрес
авторизации и ждёт код; командлет печатает адрес, человек открывает его в
любом браузере, входит, и страница показывает код, который вставляется в
stdin. Дашборд ведёт тот же диалог кнопкой «Авторизоваться» в строке
кредита claude; добавить или снять кредит со страницы нельзя, только
показать и переавторизовать (#285, #294). Сервис это держит сам:
`credreg.login_start`, через который ходят страница и глагол
`cred_login_start`, отказывает имени, которого нет в реестре, до дома и
клиента (#295) — иначе удачный код завёл бы новый кредит мимо `mop cred`.

Что собрано первым прогоном и держится в `tests/credlogin.py`:

* адрес берётся из гиперссылки OSC 8, а не из текста: терминал переносит
  его по строкам вперемешку с управляющими последовательностями
  (у `auth login` гиперссылка без id с терминатором BEL, у `setup-token` —
  с id и ST); откат — склейка строк без пробелов;
* окно pty широкое (4000 колонок), иначе переносится и гиперссылка;
* код вводится отдельно от Enter, с паузой, и ответа ждём до двух минут:
  код одноразовый, убитый раньше клиент его сжигает;
* итог `auth login` читается документированным `claude auth status --json`
  в доме кредита (`loggedIn`, `email`, `subscriptionType`); итог
  `setup-token` — токен `sk-ant-oat01-…` в выводе;
* секреты наружу только через `Login.result`; журнал и отказы проходят
  через `mask()`.

## Что у Anthropic не документировано

Сам поток логина (адреса, client id, PKCE) — внутреннее дело клиента, мы
его не воспроизводим. Ручка лимитов `GET api.anthropic.com/api/oauth/usage`
(с `anthropic-beta: oauth-2025-04-20`) не документирована и требует
области `user:profile`: её даёт `auth login`, но не `setup-token`.
Документировано: `claude auth login|status|logout`, `claude setup-token`,
переменная `CLAUDE_CODE_OAUTH_TOKEN`.
