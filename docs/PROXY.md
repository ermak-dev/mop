# PROXY: LLM-прокси установки

Единственный LLM-сервер установки — CLIProxyAPI на контроллере (эпик #379).
Он кормит и папетов, и мастеров: подписки claude и codex и
Anthropic-совместимые ключи (GLM) за одним `/v1/messages`, пул аккаунтов,
ротация по запросам и refresh токенов — внутри прокси. mop не знает ни
провайдеров, ни имён моделей: карта моделей — `mop/common/llm.py`, адрес
сервера в `MOP_PROXY_URL`; клиентские сессии получают URL и ключ из
закрытого `client.json` выбранного сервера после `mop join`.

## Установка и настройка

Роль `deploy/roles/llmproxy` (`mop server deploy`): бинарь
пиннированной версии в `/usr/local/bin/cli-proxy-api`, юнит
`mop-llm-proxy`, конфиг `~/.config/mop/llm-proxy/` (0700, пользователь
пула). `config.yaml` рендерится **только при первой установке** — дальше
его редактирует человек панелью, и повторный рендер стирал бы правки.
Ключи генерирует deploy в `secrets/` контроллера:
`llm-proxy-client.pass` (клиентский, им представляются сессии пула;
сервис кластера читает его из закрытого файла, не из открытого unit)
и `llm-proxy-mgmt.pass` (management, не покидает сервер).
`mop join --server <адрес> <логин>` сначала проверяет личный пароль по
TLS-шине, затем по отдельному личному субъекту получает URL
`https://<сервер>:<порт>/llm` и клиентский ключ, проверяет `/v1/models` и
кладёт их в `~/.config/mop/servers/<адрес>/client.json` (0600). Ключ не
вводят отдельно и не получают через публичный HTTP или узловой `server.rpc`:
право на личный запрос есть у оператора, но не у узла или папета. Повторный
join обновляет ключ после ротации. Установка `.env` на клиентскую машину не
копируется.

## Доступ

`mop master` и `mop code` передают Claude сохранённый `tls.pem` выбранного
сервера через `NODE_EXTRA_CA_CERTS` для HTTPS-прокси. Явно заданная
пользователем переменная имеет приоритет. Если файла нет, остаётся обычное
хранилище публичных CA. Уже запущенную сессию нужно перезапустить с `--resume`,
чтобы она получила новое окружение (#412).

TLS-маршрут `/llm/` принимает тела запросов до `MOP_LLM_REQUEST_MAX_MB`
МБ (по умолчанию 64, настройка установки в `.env`). История и `/compact`
проходят через тот же маршрут: маленький лимит nginx блокирует и продолжение,
и сжатие. Claude может показать такой HTTP 413 как ошибку вложений в 32 МБ,
хотя отказ пришёл от nginx (#411).

- LLM API — `http://<контроллер>:8317`, клиентский ключ обязателен;
  management того же порта отвечает только с петли.
- Панель — через TLS-прокси сервера: `https://<сервер>/llm/`
  (одностраничник, её API — `/v8/management`, тоже с корня origin).
  Вход — management-ключ (`secrets/llm-proxy-mgmt.pass` на контроллере).
  Прямой заход с LAN на порт management не проходит (`allow-remote:
  false`) — только через этот TLS.
- Журналы пишутся в файлы (`observability.logs.logging-to-file`) — их
  читает страница журналов панели; ротация с потолком размера.

## Ключ узлам

Сервис кластера раздаёт `secrets.env` с единственной строкой
`MOP_PROXY_KEY` глаголом `write` от своего субъекта (админа): копия
каждого узла (её же сеет драйвер в новые тела) и живые тела. Отпечаток
прошлой раздачи — `~/.config/mop/proxy-key.json`; недошедший узел
держит раздачу открытой до следующего тика. Моменты: старт сервиса и
каждые 5 минут (`mop/server/proxykey.py`).

## Модели

Имена opus/sonnet/haiku обслуживают алиасы в самом прокси (панель);
карта моделей в `mop/common/llm.py` снимется, когда алиасы покроют её.
`mop doctor` видит живость прокси (группа proxy: `GET /v1/models`
клиентским ключом).
