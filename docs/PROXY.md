# PROXY: LLM-прокси установки

Единственный LLM-сервер установки — CLIProxyAPI на контроллере (эпик #379).
Он кормит и папетов, и мастеров: подписки claude и codex и
Anthropic-совместимые ключи (GLM) за одним `/v1/messages`, пул аккаунтов,
ротация по запросам и refresh токенов — внутри прокси. mop не знает ни
провайдеров, ни имён моделей: окружение сессии — `mop/common/llm.py`
(адрес из `MOP_PROXY_URL`, имя ключа `MOP_PROXY_KEY`); спека папета
собирает из него сессию без карты моделей и с включённым каталогом
(#449, `mop/server/spec.py`).

## Установка и настройка

Роль `deploy/roles/llmproxy` (`mop server deploy`): бинарь
пиннированной версии в `/usr/local/bin/cli-proxy-api`, юнит
`mop-llm-proxy`, конфиг `~/.config/mop/llm-proxy/` (0700, пользователь
пула). Панель управления (`management.html`) приезжает той же раскаткой:
это отдельный репозиторий (Cli-Proxy-API-Management-Center) со своей
нумерацией, версия — `MOP_LLM_PANEL_VERSION`; деплой кладёт ассет в
`~/.config/mop/llm-proxy/static/`, где его ищет прокси, — и тот не
скачивает «latest» при первом заходе (#523, #525). Обновление панели —
правка версии и прогон. `config.yaml` рендерится **только при первой
установке** — дальше
его редактирует человек панелью, и повторный рендер стирал бы правки.
Ключи генерирует deploy в `secrets/` контроллера:
`llm-proxy-client.pass` (клиентский, им представляются сессии пула;
сервис кластера читает его из закрытого файла, не из открытого unit)
и `llm-proxy-mgmt.pass` (management, не покидает сервер).
`mop login --server <адрес> <логин>` сначала проверяет личный пароль по
TLS-шине, затем по отдельному личному субъекту получает URL и клиентский
ключ, проверяет `/v1/models` и кладёт их в
`~/.config/mop/servers/<адрес>/connection.json` (0600, #533). Ключ не
вводят отдельно и не получают через публичный HTTP или узловой `server.rpc`:
право на личный запрос есть у оператора, но не у узла или папета. Повторный
join обновляет ключ после ротации. Установка `.env` на клиентскую машину не
копируется.

Выданный адрес — канонический origin `https://<сервер>:<порт>` без `/llm`
и без `/v1` (#547; до него сервер выдавал `https://<сервер>:<порт>/llm`).
Контракт один для всех, реализован в `mop/common/llm.py`:

- сохранённый в профиле адрес и `ANTHROPIC_BASE_URL` — origin без `/llm`
  и без `/v1`; суффикс `/v1/<ресурс>` надстраивает потребитель, и ровно
  один раз (`endpoint` не удваивает `/v1` у базы, которая им уже
  кончается);
- легаси-префикс `/llm` снимается при чтении только у известного
  издателя: https, хост выбранного сервера и проверенный порт от профиля
  или настроек (неявный 443 считается сохранённым «443»). Чужой хост,
  чужой порт, http и чужой кастомный путь (`/llm` которого — его
  собственное дело) не трогаются вовсе;
- база, кончающаяся `/v1`, для `ANTHROPIC_BASE_URL` — отказ: клиент
  достроил бы `/v1/v1` молча.

## Доступ

`mop master` и `mop code` передают Claude сохранённый `tls.pem` выбранного
сервера через `NODE_EXTRA_CA_CERTS` для HTTPS-прокси. Явно заданная
пользователем переменная имеет приоритет. Если файла нет, остаётся обычное
хранилище публичных CA. Уже запущенную сессию нужно перезапустить с `--resume`,
чтобы она получила новое окружение (#412).

TLS-маршруты `/llm/` и `/v1/` принимают тела запросов до `MOP_LLM_REQUEST_MAX_MB`
МБ (по умолчанию 64, настройка установки в `.env`). Маршрута два, и у них
разная судьба:

- `/v1/` — канонический маршрут LLM API от корня origin, без среза
  префикса: панель получает каталог по `/v1/models` (#529), клиентский код
  после #547 ходит сюда от выданного origin. Клиентский ключ обязателен;
  ответы передаются без буферизации. История и `/compact` проходят через
  тот же маршрут: маленький лимит nginx блокирует и продолжение, и сжатие.
  Claude может показать такой HTTP 413 как ошибку вложений в 32 МБ, хотя
  отказ пришёл от nginx (#411).
- `/llm/` — временный алиас того же API со срезом префикса: он кормит
  клиентов на коде до #547 и уже запущенные сессии, державшие
  `ANTHROPIC_BASE_URL` c `/llm`. Снимается отдельным шагом перехода (см.
  ниже); панель и управление (`/llm/management.html`, `/llm/raw/`,
  `/v8/management`) — другой контракт и остаются при своём префиксе.

- LLM API — `http://<контроллер>:8317`, клиентский ключ обязателен;
  management того же порта отвечает только с петли.
- Панель — через TLS-прокси сервера: `/llm/management.html` ведёт в
  авторизованный шлюз `mop-web`, который проверяет роль admin и проксирует
  `/v8/management/` на петлю. Ключ management остаётся только на сервере:
  закрытую копию для шлюза кладёт роль web. Прямой заход с LAN на порт
  management не проходит (`allow-remote: false`), а nginx не пропускает
  обходные пути через `/llm/v8/management`.
- Журналы пишутся в файлы (`observability.logs.logging-to-file`) — их
  читает страница журналов панели; ротация с потолком размера.

## Переход на канонический origin и снятие алиаса /llm (#547/#546)

План, не live-проверка: ни один шаг ниже не прогонялся на живой
установке. Клиентский URL-контракт уже в дереве (#547, merge `214eeef`
эпика #531); nginx-алиас `/llm/` пока жив. Порядок для оператора:

1. **Раскатка эпика.** `mop server deploy` с деревом после #547: сервер
   выдаёт `cluster._client_config` origin без `/llm`, новый клиентский
   код строит endpoint'ы от корня origin — ходит на `/v1/`. Алиас не
   трогается: старые клиенты продолжают работать через него.
2. **Старые клиенты.** Код до #547 вычислял `/llm/v1/...` сам и ходит
   через алиас, пока не обновится. Профили, где сохранён легаси-адрес с
   `/llm`, читаются канонизацией при каждом употреблении
   (`llm.origin`/`llm.endpoint` снимают префикс у известного издателя),
   так что даже старый профиль с новым кодом ходит на `/v1/`; повторный
   `mop login` перезапишет профиль выданным origin. Уже запущенные
   сессии держат свой `ANTHROPIC_BASE_URL` с момента подъёма до
   перезапуска (`--resume`), автоматически их никто не убивает.
3. **Критерий окончания перехода.** Отдельной директивы `access_log` в
   `mop.conf.j2` нет ни в server, ни в location — но наследуется
   журнал уровня http из `/etc/nginx/nginx.conf` дистрибутива (deploy
   этот файл не трогает): обычно `/var/log/nginx/access.log` в формате
   combined, где `/llm/v1/...` и `/v1/...` различимы по полной строке
   запроса, а заголовок Authorization в журнал не попадает. Живьём это
   не проверено: оператор подтверждает фактический журнал установки
   командой `nginx -T` (секция access_log). Критерий: за выбранное
   оператором окно наблюдения в журнале нет запросов к `/llm/v1/`.
   Папеты алиаса не касаются: с #557 их `ANTHROPIC_BASE_URL` —
   публичный origin установки (см. «Папеты на публичном /v1», #557).
4. **Снятие алиаса.** Убрать `location /llm/` из mop.conf.j2 и перечитать
   nginx — но не просто удалить: после удаления запросы `/llm/v1/*` уйдут
   в `location /` к mop-web, и опоздавший клиент получит чужой ответ
   вместо явного отказа. Поэтому бывший API-префикс закрывается
   префиксным блоком с отказом: `location ^~ /llm/v1/ { return 410; }` —
   точный `location = /llm/v1/` ловит только сам `/llm/v1/` и не ловит
   `/llm/v1/messages`. Лучше закрыть весь бывший API-префикс `/llm/`
   отказом, сохранив маршруты панели (`/llm/management.html`,
   `/llm/raw/`, `/llm/v8/management`-запреты — панель и управление при
   своём префиксе). Без HTTP-редиректа: старый адрес отсылался бы молча
   на новый и скрыл живого опоздавшего от критерия шага 3.

## Папеты на публичном /v1 (#557)

Папеты ходят к LLM не на внутренний порт прокси, а на публичный origin
установки — тот же адрес, что выдают мастерам: `https://<MOP_SERVER_LAN>
:<MOP_HTTPS_PORT>` (`llm.public_origin`, единственная формула; порт
пишется явно, даже когда он 443). Дефолт `MOP_PROXY_URL` пуст: значение
в `.env` — осознанный чужой прокси, и оно проходит насквозь как есть.
Собственный внутренний корень установки (её authority плюс
`MOP_LLM_PROXY_PORT`, путь пуст, scheme любой) — это адрес мимо TLS, и
`llm.to_public_origin` канонизирует его в публичный origin; всё чужое
(путь, чужой хост или порт, учётные данные) не трогается. Установка со
старым значением `MOP_PROXY_URL=http://<сервер>:8317` переезжает без
правки `.env`: значение узнаётся и канонизируется; строчка, ставшая
лишней, уходит при следующей уборке.

Серверные читатели (каталог моделей шлюза mop-web) ходят не публичным
origin через TLS, а петлёй `http://127.0.0.1:<MOP_LLM_PROXY_PORT>`
(`llm.internal_loop`): потребитель стоит на самом контроллере рядом с
прокси, TLS и пин CA ему не нужны. Порт читается из юнитов `mop-web` и
`mop-cluster` (`SERVER_SCOPED`, раздаёт deploy).

Условие перехода: сертификат TLS-прокси обязан быть выписан для имени
`MOP_SERVER_LAN` (CN или SAN; оператор проверяет своей установкой:
`openssl x509 -in <cert> -noout -subject -ext subjectAltName`).
Сертификат только для `localhost`/IP, на который папеты не ходят, —
отдельная настройка `MOP_PROXY_URL` или перевыпуск сертификата. Корень
закрепления доезжает до тел раздачей secrets.env (см. «Ключ узлам»).

## Ротация management-ключа

Шлюз панели (#417/#418) читает закрытую копию ключа
(`~/.config/mop/secrets/llm-proxy-mgmt.pass`, кладёт роль web) при
каждом запросе; сам прокси держит ключ bcrypt-хэшем в `config.yaml`,
который deploy рендерит только при первой установке. Поэтому смена
ключа — два согласованных шага руками оператора, deploy между ними
не синхронизирует:

1. положить новый ключ в `config.yaml` прокси (`management.secret-key`,
   plaintext — прокси поднимет его без рестарта, захэширует и перепишет);
2. тем же движением обновить исходный `secrets/llm-proxy-mgmt.pass` на
   контроллере и прогнать `mop server deploy` — обновится закрытая копия
   шлюза.

Пока шаги не сделаны оба, шлюз и прокси расходятся в ключах: шлюз
получает 401. Не ретраить и не долбить: прокси банит по clientIP после
пяти неудач на полчаса, а весь трафик шлюза для него — петля, бан
закрыл бы и панель человеку. Развёртывание после запуска CLIProxyAPI делает
один скрытый (`no_log`) запрос к management API с ключом из копии шлюза:
при рассинхроне оно останавливается, а не повторяет запрос до бана.

## Ключ узлам

Сервис кластера раздаёт `secrets.env` глаголом `write` от своего
субъекта (админа): копию каждого узла (её же сеет драйвер в новые тела)
и живые тела. Файл — строки `MOP_PROXY_KEY` (обязательно) и
`MOP_PROXY_CA` (когда сервер пинит цепочку, #557): корень закрепления
в base64-PEM, декодируется врапером в `~/.config/mop/tls.pem` тела и
едет claude переменной `NODE_EXTRA_CA_CERTS` — как у мастеров (#412).
Источник корня — `proxykey.ca_source` по семантике #517: `MOP_TLS_CA`
(частная CA), самоподписанный `secrets/tls.pem` при пустом
`MOP_TLS_CERT`, отсутствие строки — настоящий сертификат с системным
доверием. Оба писателя (тик раздачи и доставка ротации) рендерят файл
одним `proxykey.blob`. Отпечаток прошлой раздачи —
`~/.config/mop/proxy-key.json`; недошедший узел держит раздачу открытой
до следующего тика. Моменты: старт сервиса и каждые 5 минут
(`mop/server/proxykey.py`). Владельцы и читатели хранилищ ключа —
[CONFIG.md](CONFIG.md).

## Владение и ротация клиентского ключа (#537)

Контракт по исходникам, не live-проверка. Доказательства закреплены:
upstream CLIProxyAPI, git-тег v8.0.16, коммит
a2976eb8a303f11b4ea5177bce9f9ff752634dfc, архив
https://github.com/router-for-me/CLIProxyAPI/archive/refs/tags/v8.0.16.tar.gz
(репозиторий router-for-me/CLIProxyAPI), sha256
97626b68af9c789a9686c41439c732b9377adffe10c2329e55092081fd339752.
Ниже — свойства протокола, прочитанные из исходников этой версии:
это не гарантия живой установки (её поведение проверит реализация
#539) и не разрешение на ротацию или реализацию. Раздел плановый
(эпик #531), реализация разнесена на #538/#539/#540.

Владелец клиентского ключа — сервер: источник —
`secrets/llm-proxy-client.pass` на контроллере (генерирует deploy,
`lookup('password')`), а живёт ключ в нескольких копиях с разными
настройщиками:

- `config.yaml` прокси (`access.api-keys`) — после первой установки
  правит человек панелью или management API; гейтвей подменяет
  серверным значением только `management.secret-key` (#417), секцию
  `access.api-keys` guard пропускает как есть — панель может сменить
  клиентский ключ без ведома mop;
- закрытая копия сервиса кластера — её кладёт роль cluster прогоном
  deploy; сервис перечитывает копию при каждой раздаче, без рестарта;
- копии узлов (`secrets.env`) и живые тела — раздача тика (#391),
  свежие тела сеются с копии узла (`MOP_BODY_SEED`);
- клиентские профили мастеров (`connection.json`) — повторный
  `mop login`.

Разъезд копий ловит один health-check прогона deploy (ключ из
`secrets/` против `GET /v1/models`): смена `access.api-keys` панелью
без смены источника оставляет источник и раздачу на прежнем ключе, и
следующий прогон останавливается.

Находки upstream (файлы и строки — исходники тега v8.0.16):

- перечитывание `config.yaml`: fsnotify на самом файле
  (internal/watcher/events.go:29-37) с дебаунсом 150 мс
  (internal/watcher/watcher.go:103); сохранение через management API
  применяет конфиг асинхронной горутиной
  (internal/api/handlers/management/handler.go:219-236). Ответ GET
  списка ключей не доказывает применения — доказывает реальный
  запрос;
- клиентский ключ проверяется множеством `access.api-keys`
  (internal/access/config_access/provider.go:36-47, 55-104): список
  из старого и нового принимает оба одновременно;
- запись секции адресная: PUT
  /v8/management/config/access/api-keys (тело — список целиком, PATCH
  — слияние; internal/api/handlers/management/config_v8.go:64-141,
  docs/management-api-v8.md:39);
- условной записи у management API в исследованном интерфейсе не
  найдено, протокол на неё не полагается: обработчик config-записей
  читает и пишет безусловно (config_v8.go:64-141), условные заголовки
  (ETag/If-Match/If-Unmodified-Since) кодом management-маршрутов не
  разбираются — единственные ревизии в конфиге это read-only поля
  Home, запись которых отвергается (config_v8.go:145-156), токеном
  сравнения они не служат. Отсюда обязательный exclusive-writer режим
  ротации;
- GET /v8/management/observability/usage/api-keys — счётчики по
  ключам в памяти (internal/api/handlers/management/
  api_key_usage.go:56-96; маршрут
  internal/api/server_management_v8.go:40): рестарт прокси их
  сбрасывает, offline-клиентов не видно — отсутствие трафика со
  старым НЕ доказывает, что его никто не держит;
- пустой список `access.api-keys` валидация НЕ отклоняет
  (internal/config/config_v8.go:855-908), и он открывает прокси без
  ключа: провайдер запросов снимается
  (internal/access/config_access/provider.go:20-24), а пустое
  множество провайдеров пропускает все запросы
  (sdk/access/manager.go:50-52). Пустой список — запрет всегда.

Ротация — операция с единственным писателем: на её время панелью
никто не пользуется. У upstream нет CAS, и read-modify-PUT без этой
дисциплины конкурирует с записями панели; безопасная автоматическая
ротация при конкурирующих писателях невозможна и не обещается.
Preflight: управляемый mop старый ключ обязан совпадать с источником
(`secrets/llm-proxy-client.pass`), присутствовать в прочитанном
списке и приниматься прокси. Расхождение — явный drift, и решает его
оператор ДО изменения: самовольное возвращение ранее отозванного
ключа в список — не шаг операции (возврат отозванного — осознанное
решение, см. ниже).
Шаги:

1. Прочитать текущий список ключей и дописать новый, сохранив ВСЕ
   прочитанные — mop управляет не всем списком, ключи, заведённые
   панелью, не его собственность. Прочитанный список пуст или
   целиком нечитаем — отказ: пустой список не пишем никогда.
2. Подтвердить реальными запросами `GET /v1/models`: новый принят и
   старый по-прежнему принят, а заведомо неверный клиентский ключ НЕ
   принят — последнее принципиально при пустом списке: он открывает
   прокси всем, и «принимаются оба» без негативной проверки не
   доказывает включённую авторизацию. Это плановая проверка
   контракта, не реальные вызовы сейчас.
3. Сменить источник и установленную копию: `secrets/
   llm-proxy-client.pass` на контроллере и закрытую копию сервиса —
   оркестрацией самой операции (план #539), не полным deploy'ом как
   штатным шагом; health-check при этом зелёный: старый ещё в
   списке. Отказ до перезаписи копии кластера оставляет раздачу на
   прежнем ключе.
4. Раздать: тик (каждые 5 минут) понесёт новый блоб узлам и живым
   телам по отпечатку; свежие тела сеются с копии узла; мастера —
   повторный `mop login`. Тела, поднятые до доставки, ходят старым —
   он ещё в списке.

Исход PUT и проверки доступа оценивается раздельно. Только отказ
ДО применения записи, подтверждённый контрактом конкретного
обработчика, означает, что этот PUT не применён. 401/403
управленческого PUT — проблема доступа; это не повод генерировать
другой ключ. 401 проверки `/v1/models` означает лишь, что ключ не
принят в момент проверки: список уже мог сохраниться, а
асинхронное применение ещё не завершиться. Источник не
переключается; выполняются ограниченные повторные проверки, затем
операция остаётся pending/failed с причиной. Timeout, разрыв
соединения и прочие неясные исходы сохраняют состояние операции;
после восстановления перечитывается список и проверяется
фактический доступ. Если тот же новый ключ отсутствует, при
действующем exclusive-writer условии обновляется СВЕЖЕПРОЧИТАННЫЙ
список, сохраняя все его ключи и добавляя тот же сохранённый ключ.
Если ключ есть, повторяется проверка применения. PUT одного списка
сам по себе идемпотентен: опасность слепого повтора не в
дублировании, а в перезаписи чужих изменений устаревшим списком.
Ни любой HTTP-ответ, ни неудачный probe не разрешают общий
автоматический rollback или генерацию другого ключа.

Штатная ротация ЗАКАНЧИВАЕТСЯ на old+new, и это состояние
требуется целиком: оба ключа подтверждённо приняты прокси,
источник и закрытая копия согласованно держат новый, доставка
подтверждена каждым предусмотренным получателем — ответ агента
узла «OK», а узел, не ответивший вовсе («NOT REACHED»), или
отказавший оставляет раздачу открытой и операцию — не завершённой
(частичная раздача не «completed»: недошедшие узлы и тела так и
ходят старым). Требование «FAILED держит операцию открытой» —
ЦЕЛЬ #538: сегодняшний `proxykey.settled` отвергает только
NOT REACHED, отказ агента FAILED он завершением считает — разница
с контрактом выше названа, чтобы план её закрыл. Обновлённый
`secrets.env` ≠ узел перечитал его:
живые сессии держат ключ с момента подъёма (`spec.py` читает
`secrets.env` врапером при старте), поэтому old+new обязателен до
отдельного retirement. Удаление старого — отдельная операция с
явным подтверждением оператора: ни время, ни счётчики usage её сами
не разрешают (счётчики сбрасываются рестартом, offline-держателей
не видно), и оператор признаёт, что неизвестные клиенты могли
сохранить старый — им нужен re-login или перезапуск.

Откат: старый и после шага 4 остаётся в списке, возвращать его туда
не нужно; восстанавливается источник и установленные копии
(`secrets/`, закрытая копия сервиса, раздача узлам) прежним
значением. Новый ключ из списка не удалять, если его уже держат
клиенты — иначе они теряют доступ без вины. После отдельного
retirement старый технически можно вернуть записью, но при ротации
из-за компрометации он недопустим: возврат скомпрометированного
ключа — осознанное решение оператора, не штатный шаг протокола.

Management-ключ — отдельный протокол (раздел выше), автоматизации в
первую очередь не подлежит (#538 ограничен клиентским ключом): в
`config.yaml` лежит bcrypt-хэш (internal/config/config_load.go:
116-131 — plaintext захэшируется и перепишется при загрузке;
internal/config/config_validation.go:65-77), не равный выдаваемому
секрету; восстановить секрет из хэша нельзя, источник правды —
`secrets/llm-proxy-mgmt.pass` и закрытая копия шлюза. Бан — 5
неудач на 30 минут по clientIP (internal/api/handlers/management/
handler.go:302-303) — только на попытки management с петли;
клиентские 401 на `/v1/` баном не караются.

Авто-отзыва старого ключа, перевода живых стрим-сессий на новый и
обратного API перечисления клиентов в upstream нет. Фактическое
перечитывание нашей установки и поведение панели при записи секции —
не проверено; проверяется глаголом #539.

План (эпик #531): #538 — примитивы ТОЛЬКО клиентского ключа
(автоматизация management — отдельное решение позже): план шагов,
генерация, приватное состояние операции для возобновления после
сбоя (новый ключ и достигнутый шаг — отпечатка одного ключа
недостаточно), проверка принятия до выдачи, сохранение неуправляемых
ключей списка; #539 — глагол CLI: оркестрация в библиотеке ведёт
источник, установленную копию и раздачу с явными контрольными
точками — без subprocess-вызовов командлетов и без совета «теперь
руками deploy»; шаг, для которого контролируемого пути нет, — блокер
и отдельный тикет; границы операции (переприсоединение мастеров,
перезапуск живых сессий, отдельный retirement) называются в итоге, а
не выполняются руками как её продолжение; #540 — deploy: причина
рассинхрона в отказе health-check по имени, запрет записи пустого
списка.

## Модели

`mop master` и `mop code` включают обнаружение моделей шлюза Claude Code:
выбор берётся у прокси **выбранного сервера**, без статического алиаса GLM.
Унаследованные модельные алиасы снимаются при новом запуске, а явный
`--model` передаётся Claude без изменений. `mop server doctor` проверяет
живость прокси (`GET /v1/models` клиентским ключом), но не выбирает модель.

`mop models` показывает актуальные ID моделей выбранного сервера через
`GET /v1/models` с его клиентским ключом; мастер получает тот же список
через read-only инструмент `models`. Каталог прокси может включать модели,
непригодные для Claude Code; команда не проверяет их совместимость. Ключ не
выводится, а запрос не следует перенаправлениям.

Папет не получает карты моделей: спека (`spec.gateway_env`) сбрасывает
слоты `ANTHROPIC_DEFAULT_*_MODEL` и включает каталог
(`CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`) — сессия папета
выбирает из живого `/v1/models`, как её видит мастер (#449). Карта в
`llm.env()` остаётся мастерской сессией. `mop doctor` видит живость
прокси (группа proxy: `GET /v1/models` клиентским ключом).
