# SOUL: декларативные роли папетов

Контракт эпика #578: все сессии пула — папеты с ролями (master, puppet,
builder…), роль описана декларативно и проверяется сервером. Сегодня
«мастер» — отдельный запуск claude на машине оператора
(`mop/cli/core/master.py`), права которого — креды человека; контракт
переносит и эту роль в пул, не давая ей прав оператора. Документ —
проектный: реализация разложена по детям (#580–#590, #592), текущий код
им не соответствует. Существующие документы описывают нынешнее поведение
и меняются каждым ребёнком в его слое.

## Граница доверия — честная

Три факта, которые контракт обязан называть, а не прятать:

1. **JWT шины без exp** (docs/BUS.md, callout): транспортный отзыв прав
   действует со следующего входа; живое соединение свой ACL не отдаёт.
   Контракт не обещает мгновенного транспортного отзыва — отзыв глаголов
   см. в разделе про реестр привязок.
2. **Драйвер host — без изоляции** (mop/driver/host.py): тела одного
   узла и UID — соседи с общим HOME; файловые права 0600 одного UID не
   защищают. Права ролей не защищают mutually untrusted папетов на host.
3. **Глаголы RPC — полезная нагрузка** под одним субъектом
   `node.<p>.<node>.rpc.<вызывающий>`: allow на субъект открывает все
   глаголы канала; тонкие права проверяет получатель.

Ответ — два уровня прав: транспорт (ACL соединения: какие субъекты) и
запрос (проверка глагола получателем по реестру привязок сервера). Роль с
требованием изолированного тела (`runtime.driver: isolating`)
размещается только на драйвере с `IS_CONTAINER = True` — решение принимает
placement по способности драйвера (mop/driver/__init__.py:502), не по
имени роли; на host такие роли не размещаются вовсе. Роли с
`driver: any` на host — доверенные жильцы одного оператора, и это
написано в каталоге.

## Четыре имени — не одно

| Понятие | Что это | Где живёт |
|---|---|---|
| Puppet ID | имя джоба `pu-<проект>-<n>` | Nomad; стабильное, может быть переиспользовано после delete |
| Incarnation | UUID, выданный при регистрации | Meta джоба (`soul_inc`); переживает рестарты и respec; delete + новая регистрация (даже с тем же именем) = новая инкарнация |
| Conversation | разговор claude в теле (`~/.claude`) | переживает рестарт обёртки через возобновление (`--continue`); новый — при старте без продолжения или пересоздании тела |
| Delivery address | инбокс на шине | `_INBOX` соединения — у каждой роли свой; люди-мастера дополнительно слушают маску `master.<токен>.>` (#213) |

Хозяин-человек (human owner) — не имя папета: это логин оператора, чья
аренда и чья git identity стоит в клоне (LEASE.md, #161/#167/#574).
Принципиал (principal) — имя шины, под которым роль входит: люди — логин,
папеты — делегированный принципал `grant-<id>` (ниже).

## soul.yaml — схема v1

Каталог роли — каталог скилла: `skills/<role>/` из пакета (см. упаковку)
или внешний каталог установки. Ровно два файла: `soul.yaml` и файл
промпта. Версия схемы — обязательное целое; сервер знает ровно свои
версии и молча новые не принимает.

```yaml
soul: master              # [a-z][a-z0-9-]*, уникален в каталоге
version: 1                # версия схемы, целое
runtime:
  driver: isolating       # any | isolating; isolating -> только IS_CONTAINER
  receives_dispatch: false # цель dispatch: на эту роль диспетчерить нельзя
capabilities:
  node_verbs: [send, tail, state, states, ping, local]  # allowlist глаголов агента (таблица VERBS)
  cluster_verbs: [roster, add]  # allowlist глаголов сервиса кластера (add, alloc, roster, update, spec…)
  dispatch: true           # источник dispatch: может занимать аренду цели (#574)
  spawn: [puppet, builder] # роли, которые эта может поднимать
prompt: soul.md            # единственный файл промпта, путь внутри каталога роли
```

Пример выше — поставляемая мастер-роль: изолированное тело, диспетчерит
на рабочих, сама не диспетчеризируема (`receives_dispatch: false`) —
задания ей ставит человек-оператор своими инструментами (ворота аренды
для человека прежние, LEASE.md). Две другие поставляемые роли —
минимальные, чтобы схема не оставляла простора для толкований:

```yaml
soul: puppet               # рабочий: принимает dispatch, ничего не поднимает
version: 1
runtime: {driver: any, receives_dispatch: true}
capabilities:
  node_verbs: [send, tail, state, states, ping, local]
  cluster_verbs: []
  dispatch: false          # рабочий не диспетчерит: получает задание, отчитывается
  spawn: []
prompt: soul.md
```

```yaml
soul: builder              # собирает в своей ветке, не управляет пулом
version: 1
runtime: {driver: any, receives_dispatch: true}
capabilities:
  node_verbs: [send, tail, state, states, ping, local]
  cluster_verbs: []        # ни add, ни alloc, ни spec
  dispatch: false
  spawn: []
prompt: soul.md
```

Два списка глаголов вместо одного: таблица агента (VERBS) и сервис
кластера — разные таблицы, и право на них выдаётся порознь
(`node_verbs`, `cluster_verbs` — точные имена глаголов своих сервисов).
Право источника (`dispatch`) и право цели (`receives_dispatch`) — разные
поля: диспетчер разрешён, только когда у вызывающего есть `dispatch`, а
у цели — `receives_dispatch` и тот же проект. `spawn` в проверке цели
не участвует: он создаёт право на подъём ролей, а не адресную книгу
диспетчера — перекрёстные задания ролей одного проекта ограничиваются
владельцем и арендой, а не списком spawn (см. dispatch ≠ send).

Никаких прав по имени роли: `soul: master` — строка, а не привилегия;
всё, что роль может, перечислено в схеме, и проверяет это сервер. Мастер-
папет не получает ни узловых глаголов (`disk`, `junk`, `sweep`), ни
субъектов админа: admin — человеческая роль оператора (operators.py,
`mop.admin.>`).

Минимализм сознательный: без наследования ролей, без переменных
окружения в soul.yaml (окружение тела — sandbox.yaml проекта и
bootstrap.yaml, как сегодня), без условных выражений. Новая потребность —
новое поле с версией схемы.

## Digest и бандл роли

Каталог роли закрепляется бандлом: сервер при регистрации кладёт
копию двух файлов в хранилище по дайджесту и больше её не меняет. Digest —
sha256 по точной канонической сборке (считает один общий модуль, #580):

```
digest = sha256(
    compact_json(manifest)   # soul.yaml, разобранный в словарь;
                             # json.dumps(…, sort_keys=True,
                             # separators=(",", ":"), ensure_ascii=False)
                             # в UTF-8
    + b"\x00"                # разделитель
    + prompt_bytes)          # сырые байты файла промпта (UTF-8)
```

Никакого «нормализованного YAML» и «всех файлов каталога»: вход дайджеста —
ровно разобранный манифест и сырой промпт. Digest пишется в Meta джоба
(`soul_digest`) при регистрации и закрепляет бандл: живая инкарнация
продолжает работать со своим бандлом и после обновления пакета ролей —
обновление каталога касается новых регистраций, а не работающих.
Enforcing сравнивает digest в Meta с бандлом в хранилище сервера, а не с
текущими байтами каталога. Локально отредактированный YAML, чужой файл в
теле или self-declared роль в сообщении не дают ничего: обёртка
стартует с промптом бандла, закреплённого в Meta, расхождение — громкий
отказ на старте (readiness).

## Принципалы, реестр привязок, отзыв

Сегодня папеты проекта входят одним паролем `puppet-<проект>`
(callout.PuppetProvider) — агент видит, о ком спросили, не кто спросил.
Контракт: одна инкарнация — один принципал.

- Bus-пользователь: `grant-<id>`, id — 32 знака нижнего hex из
  криптографического генератора, выдан при регистрации. Публичный
  идентификатор и пароль — разные вещи: id виден в логах и реестре,
  пароль — отдельная случайная строка той же силы, хранится на сервере
  приватным файлом 0600 рядом с реестром (тот же образец, что файлы
  паролей машин, pass_file), сравнение — constant-time, значения не
  попадают ни в вывод, ни в спеку. Токен не «непередаваемый» — это не
  криптографическое свойство, а политика: creds принципала в тело
  приезжают только bootstrap-ответом при подъёме (#590). Префикс
  `grant-` новый и зарезервирован (busnames.RESERVED_PREFIXES);
  принципал не разбирается суффиксом — имя проекта и роль принципала
  знает только реестр, потому и нет коллизии с легаси-проектами вида
  `foo-1`.
- Реестр привязок — файл сервера, запись: принципал → {owner, project,
  job, soul_inc, soul_digest, role, active}. Пишет регистрация (#582),
  читают callout и сервис кластера; общие кодировки — общий модуль
  (#580). `soul_inc` стабилен между рестартами инкарнации.
- Пароль принципала в тело приезжает только на подъёме, тем же
  bootstrap-ответом, что и сегодня возит проектные креды
  (mop/cli/driver/run.py, слой #590); узел его не хранит. Эмитент —
  сервер, раздача по образцу proxykey (#391): ниже сервера никто не
  выдаёт кредов.
- Переиспользование имени джоба даёт новую инкарнацию, новый id и новый
  пароль: живое соединение старой инкарнации не выдаёт себя за новую —
  оно и входом-то больше не входит, а его субъекты токенизированы.

Отзыв права — две честные ступени:

1. Глагольный отзыв: сервер ставит в записи `active: false`. Любая новая
   операция отказана: узел и сервис кластера перед мутациями спрашивают
   сервер (резолвер, ниже), ответ «не активен» — отказ с причиной.
   Идущая работа не убивается: уже запущенный процесс в теле продолжает
   жить, новых глаголов у него нет.
2. Транспортный отзыв: удаление файла пароля — следующий вход отказан;
   живое соединение держит свой ACL до переподключения (факт 1 выше),
   и это написано прямо, без обещаний. Уже доставленные в тело секреты
   отозвать нельзя — байты у папета; это тоже написано, а не спрятано
   (#592).

Резолвер привязок — доверенный, на сервере. Узловые креды в `cluster.rpc`
публиковать не могут — существующий инвариант шины (natsconf.node_permissions:
узлу даны `server.rpc` и `node.msg`, кластер — только людям), и контракт
его не ломает. Поэтому резолвер — глагол серверного bootstrap-сервиса
(`mop.<проект>.server.rpc`, тот же сервис, что сегодня отвечает `identity`,
LEASE.md): узел зовёт его от узлового креда — «принципал P, глагол V на
цели T» → {роль, digest, активность, права}. Сервис кластера резолвит той
же серверной библиотекой in-process: резолвер один, зовут его два пути —
шина для узла, прямой вызов для кластера. Новых прав над Nomad у узла не
появляется: ответ резолвера — данные, не операции. Узел не хранит каталог
и не спрашивает Nomad, которого у него нет; сервер не импортирует узел —
только шина. Кэш — только для читающих глаголов и не дольше настройки
(короткий TTL); мутации (dispatch, spawn, write) разрешаются без кэша,
запросом.

Поля авторитета не приезжают в теле запроса: всё служебное (`_caller`,
`owner`, роль, digest, инкарнация) получатель или срезает, или берёт из
субъекта и резолвера — тело запроса ненадёжно в обоих мирах, легаси и
новом (#207 так и делает сегодня).

Права принципала на соединение рендерит callout из реестра (#581).
Транспорт нового принципала — только свой токен: публикация в
`node.<p>.<узел>.rpc.<свой grant-id>` для глаголов из `node_verbs` и,
при `dispatch: true`, в `node.<p>.<узел>.dispatch.<свой grant-id>`
(пустые списки прав — ни одного rpc-субъекта), публикация в инбоксы
адресатов и подписка на собственный инбокс — всё. Легаси-набор
`puppet-<проект>` — анонимные `node.msg` всем узлам, broadcast, events —
новым принципалам не достаётся вовсе: иначе send/read/резолвер обходятся
соседским `.msg`, и весь запросный уровень становится необязательным.
Легаси-креды проекта живут отдельно, как сегодня (natsconf.puppet_permissions),
пока оператор не переведёт проект. Прежние широкие субъекты без логина
(#207-переход) остаются только у легаси-людей и в ACL делегированных
принципалов не попадают. Сервис кластера проверяет `cluster_verbs` по
резолверу так же, как агент — `node_verbs`: права гранулярные на обеих
сторонах, не только на узле.

Инварианты #207/#213 сохраняются: подписка на инбоксы — только свои
(`master.<свой токен>.>`), адрес мастера — токен логина первым токеном,
`from-name` в конверте. В теле папета нет и не появляется: человеческих
паролей, `.env` установки, токена Nomad. Прокси-ключ LLM — как сегодня,
с копии узла.

## dispatch ≠ send

Сегодня `send` публичен: сосед пишет в тело, v_send захватывает аренду и
ставит git identity, публичный канал срезает владельца (#150). Контракт
разводит:

- `send` — сообщение соседу: доставка в сессию, без аренды и без git
  identity. Для новых принципалов — авторизованный rpc-запрос со своим
  токеном, если `send` есть в `node_verbs`; легаси-человеческий rpc send
  сохраняет сегодняшнюю семантику (аренда, identity, срезанный владелец)
  ровно на легаси-пути — переход его унаследует, новые роли — нет.
- `dispatch` — отдельная операция, а не «send с флагом»: свой субъект
  (`node.<p>.<узел>.dispatch.<свой grant-id>`), аутентифицированный
  вызывающий → резолвер проверяет `dispatch: true` вызывающего →
  `receives_dispatch: true` цели → аренда и git identity по #574
  (критическая секция целиком) → доставка задания. Поле `dispatch: true`
  у отправителя само по себе не превращает его ответы и обычные send'ы
  в диспетчер: режим определяет субъект операции и резолвер, а не роль
  отправителя и не тело запроса. Цель не обязана входить в `spawn`
  вызывающего: `spawn` — право подъёма ролей, а не адресная книга
  диспетчера; границу цели держат `receives_dispatch` цели, тот же
  проект и владелец/аренда.

Непривилегированный папет не может выбрать «режим запроса» и получить
аренду: режим определяет субъект и резолвер, а не тело запроса (#584).
Это закрывает и сегодняшний хвост: публичный send, снимающий владельца,
исчезает вместе с легаси-переходом.

Отдельный случай — первый ход мастер-роли: она может закоммитить ДО
первого dispatch, и identity хозяина в клоне должна стоять до первого
хода модели. Создание мастер-роли включает подготовку: сервер (или
доверенный лаунчер, #583/#590) ставит git identity хозяина из записи
реестра — owner берётся из авторизованного создания (человек или
делегировавший принципал через резолвер), не из тела запроса клиента —
тем же механизмом снимка/компенсации #574, до старта модели и без
копирования человеческих кредов в тело. Последующие dispatch сохраняют
транзакционную семантику #574 целиком.

## Git, трекер, CI, секреты — без ложных стен

- Git identity при dispatch — это подпись коммита, а не доступ: глагол
  `identity` (#167) и постановка ДО доставки со снимком, компенсацией и
  откатом (#574) остаются как есть. Булевых «git-прав» в схеме нет: шелл
  роли и так может позвать git, и pretending-поле не делает его
  привилегией.
- Трекер и CI остаются шеллом CLI роли (docs/MCP.md, #450/#515):
  универсального трекерного MCP не появляется. Координаты трекера
  резолвит `mop dev` из origin пакета с оговоркой #515 — это не «cwd
  роли», и контракт этого не утверждает.
- Секреты сегодня раздаёт bootstrap одинаково всем ролям проекта
  (sandbox.yaml, bootstrap.yaml). Ролям нужны разные наборы: у
  мастер-роли — креды трекера и CI, у рабочего — нет. Схема v1 даёт
  явный allowlist вместо обещания:

  ```yaml
  secrets:
    files: [gitlab-token]   # точные имена файлов секретов проекта
    vars:  [CI_JOB_TOKEN]   # точные имена переменных из secrets.env
  ```

  Точные имена, без масок; по умолчанию — пусто: роль без блока не
  получает ничего сверх печённого в образ. Держит фильтрацию серверный
  доверенный bootstrap: он собирает роль-частный временный каталог в
  существующем формате `files/`+`vars.env` и подаёт его текущему плейбуку
  `mop_secrets_dir` — нового плейбука, SDK и провайдера кредов в v1 нет
  (#592). Печёные в образ секреты остаются границей доверенного проекта,
  и отзыв уже доставленных байтов не обещается: смена роли в живом теле
  не стирает того, что тело уже прочитало. Граница фильтрации — доставка,
  а не память.
- Builder — агентная роль: собирает, проверяет, катит в своей ветке.
  Глагола сборки образа у роли нет: `cluster_verbs: []` по умолчанию, и
  admin-сборка (mop-builder) роли не достаётся молча — ни через схему,
  ни через «доверенное имя».
- Bootstrap — серверный Ansible, то есть код на сервере, а не данные:
  `.mop/bootstrap.yaml` из рабочей копии сегодня исполняет сервер
  (deploy/bootstrap). Делегированная роль с `cluster_verbs: [add…]`
  НЕ получает права подавать свой bootstrap: произвольный YAML,
  исполненный Ansible'ом сервера, — это серверный код от имени роли, и
  так роль самовыдала бы себе секреты серверными задачами. Регистрация
  роли применяет только серверный, операторски согласованный bootstrap
  (хранящийся на сервере, правит оператор); публикация и смена
  bootstrap-политики — власть человека-оператора, отдельного

## CLI, имена, упаковка

`mop <skill>` по умолчанию поднимает нового папета с ролью (пользователь
просит «запустить» — получает запуск). Подключение к живому — отдельная
явная команда `mop attach <name>` (tmux, как сегодня). `mop master`
заменяется общим лаунчером явно: в переходе это алиас мастер-роли,
пишущий, что он запускает; молчаливых fallback-ов нет.

Имя скилла не может затенять существующую команду или зарезервированное
имя (префиксы шины, `admin`, `service`, `callout`, `grant-`): коллизия —
громкий отказ на старте CLI (#586).

Упаковка: роли едут в пакете (`skills/<role>/`), как сегодня
skills/master; внешние роли — каталог установки, задаваемый настройкой.
Клон репозитория может нести свои роли — для установки они внешний
каталог.

## Readiness и ошибки

Старт роли отказывает громко и с причиной: нет роли в каталоге, digest
не сходится с Meta, схема новее известной, `driver: isolating` не нашёл
изоляционного драйвера, имя скилла коллизирует, принципал не найден в
реестре, привязка не активна. Отказ — до обёртки: ростер показывает
упавшее, Nomad перезапускает, как при отказе bootstrap (#62). Тихих
деградаций нет: роль без бандла не стартует с пустым промптом.

## Переход и откат

Ничего автоматического. Живые локальные мастера (`mop master`), легаси-
джобы и общие проектные креды работают как раньше, пока оператор явно
не переведёт проект; смена кредов проекта на делегированные — отдельная
перекатация с переходным окном (обе схемы входа валидны, окно закрывает
оператор).

Откат не сносит soul-джобы — это уничтожение работы. Откат — настройка
«пауза»: новых регистраций роли нет, креды и мета живых сохранены, живые
инкарнации продолжают; легаси-лаунчер остаётся явной командой.
Разрушительной миграции нет и не планируется. Смена роли или digest у
живого джоба inplace не делается: изменившаяся роль — новый папет, работа
старого сохраняется; уже доставленные секреты отозвать нельзя, и
понижение роли в живом теле не обещает стереть прочитанное.
