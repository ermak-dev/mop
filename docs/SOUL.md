# SOUL: декларативные роли папетов

Контракт эпика #578: все сессии пула — папеты с ролями (master, puppet,
builder…), роль описана декларативно и проверяется сервером. Сегодня
«мастер» — отдельный запуск claude на машине оператора
(`mop/cli/core/master.py`), права которого — креды человека; контракт
переносит и эту роль в пул, не давая ей прав оператора. Документ —
проектный: реализация разложена по детям (#580–#590), текущий код им не
соответствует. Существующие документы описывают нынешнее поведение и
меняются каждым ребёнком в его слое.

## Граница доверия — честная

Три факта, которые контракт обязан называть, а не прятать:

1. **JWT шины без exp** (docs/BUS.md, callout): отзыв прав действует со
   следующего входа. Живое соединение ACL не отберёт — и контракт НЕ
   обещает мгновенный отзыв на транспортном уровне.
2. **Драйвер host — без изоляции** (mop/driver/host.py): тела одного
   узла и UID — соседи с общим HOME; файловые права 0600 одного UID не
   защищают. Права ролей НЕ защищают mutually untrusted папетов на host.
3. **Глаголы RPC — полезная нагрузка** под одним субъектом
   `node.<p>.<node>.rpc.<логин>`: allow на субъект даёт ВСЕ глаголы,
   тонкие права проверяет получатель.

Ответ на все три — два уровня прав: **транспорт** (ACL соединения:
какие субъекты) и **запрос** (проверка глагола получателем по доверенному
каталогу). Отзыв: транспортный — при переподключении, глагольный — при
обновлении каталога у enforcing-стороны (#581, #584). Роль с требованием
изолированного тела (`runtime.driver: isolating`) размещается только на
драйвере с `IS_CONTAINER = True` — решение принимает placement по
СПОСОБНОСТИ драйвера (mop/driver/__init__.py:502), не по имени роли; на
host такие роли не размещаются вовсе. Роли с `driver: any` на host —
только доверенные жильцы одного оператора, и это написано в каталоге.

## Четыре имени — не одно

| Понятие | Что это | Где живёт |
|---|---|---|
| Puppet ID | имя джоба `pu-<проект>-<n>` | Nomad, стабильное, переиспользуется после delete |
| Incarnation | UUID, выданный при регистрации | Meta джоба (`soul_inc`), переживающий рестарты и respec; новое имя после delete — новая инкарнация |
| Conversation | сессия claude (`~/.claude` в теле) | меняется на каждый старт обёртки; «самая свежая живая» — как сегодня (#189) |
| Delivery address | инбокс на шине | `<токен принципала>` в мастеровской маске проекта или `_INBOX` |

Хозяин-человек (human owner) — не имя папета: это логин оператора, чья
аренда и чья git identity стоит в клоне (LEASE.md, #161/#167/#574).
Принципиал (principal) — имя шины, под которым роль входит: люди — логин,
папеты — делегированный принципал (ниже).

## soul.yaml — схема v1

Каталог роли — каталог скилла: `skills/<role>/soul.yaml` (роль в пакете,
см. упаковку) или внешний каталог установки. Версия схемы — обязательное
целое; сервер знает ровно свои версии и молча новые не принимает.

```yaml
soul: master              # [a-z][a-z0-9-]*, уникален в каталоге
version: 1                # версия схемы, целое
runtime:
  driver: any             # any | isolating; isolating -> только IS_CONTAINER
capabilities:
  verbs: [send, tail, state, states, ping, local]   # глаголы агента (таблица VERBS)
  dispatch: true          # может занимать аренду и ставить git identity (#574)
  spawn: [puppet]         # роли, которые эта может поднять (spawn_roles)
  git: true               # сервер ставит git identity владельца при dispatch (#167)
  tracker: false          # трекер и CI остаются шеллом роли (см. ниже)
prompt: soul.md           # единственный файл промпта внутри каталога роли
```

Никаких прав по имени роли: `soul: master` — строка, а не привилегия;
всё, что роль может, перечислено в `capabilities`, и проверяет это
сервер. `master != admin`: admin — человеческая роль оператора
(operators.py, `mop.admin.>`), мастер-папет не получает ни узловых
глаголов (`disk`, `junk`, `sweep`), ни субъектов админа.

Минимализм сознательный: без наследования ролей, без переменных
окружения в soul.yaml (окружение тела — sandbox.yaml проекта и
bootstrap.yaml, как сегодня), без условных выражений. Новая потребность —
новое поле с версией схемы.

## Digest и доверенный каталог

Digest роли — sha256 по канонической сборке: `soul.yaml` (нормализованный
YAML) + `prompt` файл + список файлов каталога с их хешами. Считает и
хранит ОДИН общий модуль (#580): сервер, узел и CLI не дублируют
кодировку. Digest пишется в Meta джоба (`soul_digest`) при регистрации.

Доверие — только каталогу, согласованному с сервером: роли читаются из
каталога установки (путь — настройка, дефолт — упакованный `skills/`
плюс явный каталог оператора). Локально отредактированный YAML, чужой
файл в теле или self-declared роль в сообщении НЕ дают ничего: enforcing
сравнивает digest в Meta с digestом каталога, расхождение — громкий
отказ на старте (readiness), а не молчаливая работа с чужим промптом.
Обёртка стартует только с промптом того digestа, что записан в Meta.

## Принципалы и делегированные креды

Сегодня папеты проекта входят одним паролем `puppet-<проект>`
(callout.PuppetProvider) — агент видит, о ком спросили, не кто спросил.
Контракт: один папет — один принципал.

- Bus-пользователь: `puppet-<проект>-<n>` (грамматика имён — busnames,
  префикс прежний `PUPPET_PREFIX`, разбор `is_puppet` расширяется).
- Пароль: файл сервера `nats-puppet-<проект>-<n>.pass`, выдаёт сервер при
  регистрации (#582), в тело приезжает ТОЛЬКО на подъёме — тем же
  bootstrap-ответом, что и сегодня возит проектные креды (mop/cli/driver/
  run.py, слой #590). Узел его не хранит.
- Отзыв — удаление файла: следующий вход отказан (честная граница выше);
  живое соединение гасится рестартом аллокации (#582).
- Эмитент и владелец ключей — сервер, раздача по образцу proxykey
  (#391): никто ниже сервера не выдаёт кредов.

Права принципала на соединение рендерит callout из каталога ролей (#581):
транспортная маска зависит от capabilities — `dispatch` даёт публикацию в
rpc-субъекты проекта со своим токеном, обычная роль — только
`node.<p>.<node>.msg` и `master.>`-инбоксы, как сегодня
(natsconf.puppet_permissions). Прежние широкие субъекты без логина
(#207-переход) остаются ТОЛЬКО у легаси-людей и никогда не попадают в
ACL делегированных принципалов.

Инварианты #207/#213 сохраняются: подписка на инбоксы — только свои
(`master.<свой токен>.>`), адрес мастера — токен логина первым токеном,
`from-name` в конверте. Делегированный принципал мастера-роли слушает
свою мастеровскую маску — отчёты его папетов адресуются ему, люди чужих
инбоксов не слышат.

В теле папета нет и не появляется: человеческих паролей, `.env`
установки, токена Nomad. Прокси-ключ LLM — как сегодня, с копии узла.

## dispatch ≠ send

Сегодня `send` публичен: сосед пишет в тело, v_send захватывает аренду и
ставит git identity, публичный канал срезает владельца (#150). Контракт
разводит:

- `send` — сообщение соседа: доставка в сессию, БЕЗ аренды и БЕЗ git
  identity. Публичный субъект `.msg`, как сегодня.
- `dispatch` — занять аренду, поставить git identity владельца (#574,
  критическая секция целиком), передать задание. Только rpc-субъект с
  токеном принципала + `capabilities.dispatch` у вызывающей роли.

Непривилегированный папет не может выбрать «режим запроса» и получить
аренду: режим определяет не тело запроса, а субъект и роль вызывающего,
проверяемая агентом по каталогу (#584). Это закрывает и сегодняшний
хвост: публичный send, снимающий владельца, исчезает вместе с
легаси-переходом.

## Git, трекер, CI — без универсального трекерного MCP (#515)

- `git: true` — при dispatch сервер отвечает git identity владельца
  (глагол identity, #167), агент ставит её ДО доставки со снимком,
  компенсацией и откатом по цепочке (#574). Ничего нового: путь уже есть.
- Трекер и CI остаются шеллом CLI мастера-роли (docs/MCP.md, #450/#515):
  универсального трекерного MCP не появляется. Координаты трекера
  резолвятся из origin рабочей копии роли — как у мастера сегодня.
- Роль НЕ получает ключей трекера от пула: креды трекера — окружение
  проекта (sandbox/bootstrap), их видит только роль с `tracker: true`,
  и это та же граница, что сегодня у мастер-шелла.

Builder — АГЕНТНАЯ роль (собирает, проверяет, катит в своей ветке), а не
образотворец: сборка образов остаётся сервисом сервера (mop-builder);
builder-роль лишь может просить сборку глаголом build через rpc
(#585).

## CLI, имена, упаковка

`mop <skill>`: поднять папета с ролью (или подключиться к живому —
resume/attach по tmux, как `mop attach`; `--new` — принудительно новый).
Имя скилла не может затенять существующую команду: коллизия — громкий
отказ на старте CLI (#586). Зарезервированы также префиксы шины
(busnames.RESERVED_PREFIXES) и имена ролей людей (`admin`, `service`,
`callout`).

Упаковка: роли едут в пакете (`skills/<role>/`), как сегодня
skills/master; внешние роли — каталог установки, задаваемый настройкой
(дефолт сегодня, значение по умолчанию равно текущему пути). Клон
репозитория может нести свои роли — для установки они внешний каталог.

## Readiness и ошибки

Старт роли отказывает громко и с причиной: нет роли в каталоге, digest
не сходится с Meta, схема новее известной, `driver: isolating` не нашёл
изоляционного драйвера, имя скилла коллизирует. Отказ — до обёртки:
ростер показывает упавшее, Nomad перезапускает, как при отказе bootstrap
(#62). Тихих деградаций нет: роль без каталога не стартует с «пустым»
промптом.

## Переход и откат

Ничего автоматического. Живые локальные мастера (`mop master`),
легаси-джобы и общие проектные креды работают как раньше, пока
оператор явно не переведёт проект; смена credов проекта на делегированные
— отдельная перекатация с переходным окном (обе схемы входа валидны,
окно закрывает оператор). Откат — удалить soul-джобы и вернуть `mop
master`: легаси-путь не удаляется в рамках эпика. Разрушительной
миграции нет и не планируется.
