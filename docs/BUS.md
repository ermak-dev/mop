# Шина пула

Как мастер разговаривает с узлами: сообщения поверх NATS. Сервер разворачивает
[deploy/setup.yml](../deploy/setup.yml), права — `deploy/nats-server.conf.j2`,
подписчик — `mop/agent.py`, клиент — `mop/bus.py`.

Шина довозит байты до узла; разговор с самой сессией claude — отдельный слой,
[CHANNEL.md](CHANNEL.md).

## Топология

```
мастер                                     узел
  bus.py ──request──> mop.node.<узел>.rpc ──> mop-agent ──> tmux / git / сокет
         <──reply───                                        сессии папета
  mop mcp <─────────  mop.master.<id>.inbox <─ агент: «папет освободился»
                                            <─ папет: отчёт, тем же субъектом
```

* Сервер NATS живёт на машине из группы `server`, рядом с сервером Nomad. В
  конфиге — LAN-адрес (`nats://<LAN>:4222`): публичное имя резолвится в роутер,
  который не делает хайрпин.
* Шина без TLS, осознанно: renew для сертификата было нечем автоматизировать, а
  этажом ниже RPC Nomad всё равно не шифрован. Проекты отделяют друг от друга
  креды и недоступность 4222 снаружи (причины — в комментариях
  `nats-server.conf.j2`).
* Мастер адресует узел, а не аллокацию: имя узла берётся из ростера Nomad
  (`NodeName` аллокации).
* Агент один на узел, под systemd, вне спеки джоба: переживает рестарт папета,
  а его правки доезжают прогоном плейбука, без перерегистрации джобов.

## Проект

Проект — один репозиторий: `puppets.project_of(origin)` — basename без `.git`;
единственное определение проекта в системе, отсюда же строятся имена папетов
(`pu-<проект>-<n>`). `admin` — не проект, а его отсутствие: так ходит оператор из
обычного шелла, все проекты плюс узловой `disk`.

Мастеров может быть сколько угодно, в том числе несколько на один проект.
`mop master` считает проект по origin рабочей копии; запущенный этой сессией
`mop mcp` наследует `MOP_PROJECT` и собирает по нему креды проекта — и срез, и
права. Креды мастера лежат не в файле плейбука, а в каталоге сервера
`~/.config/mop/servers/<MOP_SERVER_LAN>/` (`mop/creds.py`): пароли под теми
же именами, что в `secrets/` сервера. Токена Nomad там больше нет: управление
уехало за шину, и токен живёт на сервере (#82, docs/CLUSTER.md). На машину оператора
их везёт `mop join`, контроллер собирает их себе в конце `mop deploy`.
Адрес из окружения старше `.env`, так что `MOP_SERVER_LAN=<адрес> mop master`
переключает шину, Nomad и каталог кредов разом.

## Субъекты

| Субъект | Кто пишет | Что там |
|---|---|---|
| `mop.admin.node.<узел>.rpc` | оператор | всё и везде, плюс узловой `disk` |
| `mop.<проект>.node.<узел>.rpc` | мастер проекта | `state`, `states`, `sizes`, `usage`, `tail`, `type`, `send`, `wipe`, `write` |
| `mop.<проект>.node.<узел>.msg` | папеты проекта | `ping`, `local`, `state`, `states`, `send`, `tail` |
| `mop.<проект>.all.msg` | папеты проекта | то же, но всем узлам разом |
| `mop.<проект>.master.<id>.inbox` | агенты и папеты проекта | вести и отчёты конкретному мастеру |
| `mop.<проект>.master.all.inbox` | папеты проекта | опрос `who`: кто из мастеров жив |
| `mop.<проект>.events` | агенты и папеты проекта | журнал проекта: агент пишет `send`, `idle`, `type`, `wipe`, свой `up` (в `admin`); читает дашборд (docs/WEB.md) |
| `mop.<проект>.server.rpc` | узлы (`bootstrap`), мастер проекта (`put`) | сервер: bootstrap песочницы при старте папета и хранение его файла (docs/BOOTSTRAP.md) |
| `mop.<проект>.cluster.rpc` | мастер проекта, оператор | сервис кластера: Nomad за шиной — ростер, жизнь папета, узлы (docs/CLUSTER.md) |

* `all.msg` нужен потому, что послать в субъект с `*` нельзя: маска в NATS
  работает на стороне подписчика.
* `_INBOX.>` обязателен в правах обеим сторонам, иначе request-reply молча не
  работает.
* Инбокс адресуется мастером, а не проектом: `<id>` — это `<хост>-<pid>` его
  MCP-сервера, и два терминала в одном проекте не разбирают вести друг друга.
  Своё имя мастер передаёт агенту полем `reply_to` (уведомления о простое) и
  папету — конвертом (`from-name`) каждого сообщения. Мастер без живой сессии
  на инбокс не подписывается: некуда класть весть — не называйся адресом.
* Имя сессии claude адресом не является: оно выводится из каталога, не
  уникально и шине неизвестно.
* Субъект сервиса кластера заведён отдельно от субъекта сервера намеренно: в
  `server.rpc` имеет право писать агент узла, и глаголы над Nomad там значили
  бы, что джобы регистрирует и снимает любой узел.

## Креды

| Пользователь | Что может | Где лежит |
|---|---|---|
| `<человек>` | `mop.<проект>.>` каждого своего проекта (или `mop.>` при `*`) | машина оператора, `servers/<адрес>/operator.json` |
| `admin` | `mop.>` целиком | машина оператора, `servers/<адрес>/nats-admin.pass` |
| `master-<проект>` | `mop.<проект>.>` целиком | машина оператора, `servers/<адрес>/nats-master-<проект>.pass` |
| `puppet-<проект>` | пишет в `.msg`, `all.msg`, инбоксы мастеров своего проекта | узел, `bus-<проект>.json` |
| `node-<узел>` | слушает субъекты своего узла, пишет в инбоксы, события и субъект сервера | узел, `bus.json` |

Оператор — человек, а не роль (#84). Список людей и их проектов живёт в
настройке `MOP_OPERATORS` (`имя:проект,проект; имя:*`), разбирает его
`mop/operators.py`, и прогон заводит каждому пользователя с его именем.
Отозвать доступ — убрать человека из списка и прогнать deploy: пароль
остальных при этом не меняется. Входит оператор командой
`mop join --user <имя>` — пароль спрашивается и проверяется соединением, ssh
и копирование чужого каталога не нужны.

Ролевые `master-<проект>` живут рядом, пока установка не перевела всех: у них
один пароль на всех операторов проекта, и привозило его копирование каталога
по ssh (#88). `bus.config()` предпочитает `operator.json`, если он есть.

Креды отвечают ещё на один вопрос: мастер это или папет. `puppet-<проект>` в
субъект сервиса кластера не пишет вовсе, `admin` и `master-<проект>` пишут — по
этому `mop mcp` и выводит свой профиль (docs/MCP.md). Раньше он выводил его по
наличию токена Nomad — проверка отвечала верно ровно потому, что токен возили
одним мастерам; управление уехало за шину (#80, #81), и ни одна команда
оператора Nomad больше не зовёт.

Сервер (дашборд `mop-web`, подписчики `mop-bootstrap` и `mop-cluster`) ходит
под `admin`: свой
каталог кредов ему собирает роль `web`, и второго способа представиться шине у
него нет.

Папет ходит под кредом своего проекта, а не узла: агент видит, кого спрашивают,
но не видит, кто спрашивает. Файл подсовывает врапер через `MOP_BUS_CONFIG` в
`tmux -e`; нет файла — врапер валится громко. Агент проекты пересекает
сознательно (он и есть то, что их разделяет), но подписан только на свой узел:
подписка в NATS не эксклюзивна, и агент соседнего узла мог бы ответить первым.

Пользователей на проект заводит роль `bus` по реестру проектов
(`~/.config/mop/projects`, `mop/projects.py`) — единственному ответу на вопрос
«какие проекты заведены». Реестр правят `mop project add` и
`mop project delete`; они же играют `deploy/projects.yml` — узкий прогон тех
же задач роли, что играет полная установка. `mop deploy` реестр только
читает и аргументов не принимает (#79).

До реестра список собирался при каждом прогоне объединением ростера Nomad,
памяти контроллера и аргументов `mop deploy <origin>`: завод проекта
был побочным эффектом прогона, а снять проект было нельзя вовсе. Память
переносится в реестр один раз, при первом обращении, и дальше не читается.

У нового проекта пользователя ещё нет — `mop add` и `mop master` отсылают к
`mop project add <origin>`: на узел ведёт одна дорога.

## Глаголы

Набор закрыт: «выполни шелл» через шину попросить нельзя.

| Глагол | Кому | Что делает |
|---|---|---|
| `ping` | всем | жив ли агент, как его зовут |
| `state` | всем | факты об одном папете |
| `states` | всем | то же пачкой: у узла их обычно несколько |
| `sizes` | мастеру | место папетов (клон + target), du по спросу |
| `usage` | мастеру | расход токенов папетов по дням, по транскриптам claude |
| `local` | всем | какие папета вообще живут на этом узле |
| `send` | всем | сообщение в сессию папета, в ответе вердикт доставки |
| `tail` | всем | буфер tmux-пейна |
| `type` | мастеру | слэш-команда или клавиша в TUI по белому списку |
| `write` | мастеру | атомарная запись файла из белого списка путей |
| `disk` | оператору | df по ФС узла |
| `wipe` | мастеру | снести рабочую копию папета, восстановив из git; target — целиком |

Права проверяются дважды: сервером NATS (кто в какой субъект пишет) и самим
агентом (какой глагол, каким субъектом и про чьего папета — проект из субъекта
сверяется с настоящим origin клона). `disk` — узловой, живёт только в
`mop.admin.*`: место на хосте общее для всех его жильцов, и мастеру проекта
соседняя нагрузка не показывается. `type` и `write` ходят по белым спискам:
произвольная команда в чужой TUI и произвольная запись в `$HOME` — два способа
получить исполнение кода на узле.

`write` рядом с `disk` не остался. Раздача кредов (`mop login`) — тот же
глагол, и запрет означал, что мастер проекта не может починить протухший логин
своих же папетов: инструмент отбивался по каждому узлу, а `doctor` оставался
без лечения. Опасности, ради которой запрет вводили, тут нет: оба файла из
белого списка собираются из машины, а не из проекта мастера —
`.credentials.json` из логина claude.ai управляющей машины, `secrets.env` из
`.env` самого репозитория mop, — поэтому мастер любого проекта везёт байт в байт
то же, что вёз бы оператор. Папета это не расширяет: `write` не публичный
глагол, а `puppet-<проект>` в субъект `.rpc` не пишет вовсе.

## Факты и вердикты

`state` возвращает не «free», а сырьё:

```json
{"present": true,
 "screen": "…последние непустые строки пейна…",
 "session": "idle 1 1",
 "clone": {"cur": "bug/1063", "def": "master", "dirty": 0, "ahead": 2}}
```

Вердикт «free/busy/HUNG/AGENT SILENT» собирает мастер чистой функцией
`puppets.puppet_state` — вся матрица проверяется `python3 tests/state.py` без
пула. «Свободен» означает «в клоне нет несохранённой работы», а не «сессия
молчит». «Агент молчит» — отдельное состояние без лечения: папет может
работать, рестарт убьёт работу в клоне; лечится юнитом на узле, то есть
плейбуком. Отказ прав NATS приезжает в `error_cb`, а не в ответ на запрос, и
без разбора читается как «агент молчит».

## Ограничения

* `max_payload` сервера — 1 МБ; `bus.MAX_PAYLOAD` отбивает перебор понятной
  ошибкой. Это совпадает с лимитом канала claude (1 МиБ на строку), более
  узкого места в цепочке нет.
* Персистентности нет (JetStream выключен): сообщение упавшему агенту не
  доедет, уведомление, отправленное в момент перезапуска мастера, теряется.
* Заявок на доставку нет: `send` возвращает вердикт синхронно.
