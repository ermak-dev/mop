# Канал сообщений claude code

Как программно послать сообщение в живую сессию claude code и как узнать, что
она его отработала. Всё ниже вытащено из бинаря `claude` 2.1.251 и проверено на
живой сессии; помечено, что именно проверено, а что прочитано, но не пробовано.

Реализация — `bin/mop send`.

## Где сокет

У каждой сессии свой unix-сокет:

```
/run/user/<uid>/cc-socks/<pid>.sock
```

Путь пишется в файл сессии `~/.claude/sessions/<pid>.json`, поле
`messagingSocketPath`. Каталог выбирается по `XDG_RUNTIME_DIR`, с откатом на
`/tmp/cc-socks-<uid>/` (и `$PREFIX/tmp` под termux). Если полный путь не влезает
в 103 байта — лимит длины пути unix-сокета — сессия уходит на запасной вариант.

**Не путать с сокетом Chrome native host.** Процесс, который порождает браузер
для `claude-in-chrome`, кладёт свой сокет в ТОТ ЖЕ каталог и с тем же шаблоном
имени `<pid>.sock`, но говорит на другом протоколе (кадры с 4-байтовой длиной,
`ping`→`pong`, `get_status`→`native_host_version`). Живая интерактивная сессия
на `ping` не ответит. Отличать по `messagingSocketPath` в файле сессии, а не по
имени файла.

Дочерние процессы сессии получают адрес и токен прямо в окружении — это
санкционированный вход, ничего искать не надо:

```
CLAUDE_CODE_MESSAGING_SOCKET=/run/user/1000/cc-socks/861028.sock
CLAUDE_CODE_MESSAGING_TOKEN=<childToken>
```

Есть и флаг `claude --messaging-socket-path <путь>`, чтобы задать адрес явно.

## Кадрирование

NDJSON: по одному JSON-объекту в строке, разделитель `\n`.

* строка длиннее **1 МиБ** — соединение рвут;
* первая полная строка должна прийти за **30 с**, иначе соединение закрывают;
* **ответа в том же соединении не бывает.** Отправитель пишет и закрывает;
  всё, что сессия хочет сказать в ответ, она шлёт отдельным соединением на
  адрес из поля `from`.

## Авторизация

Первой строкой — необязательный кадр:

```json
{"type":"auth","token":"<32 hex>"}
```

Токен лежит рядом с файлом сессии:

```
~/.claude/sessions/<pid>.<sha256(realpath пути сокета)>.key      (0600)
{"peerToken":"…","procStart":"…","pidDomain":"…"}
```

На linux и macos auth формально не обязателен: личность отправителя сессия
берёт из `SO_PEERCRED` (`verifiedPeerPid` + владелец сокета). На windows
обязателен. **Но права разные:** без токена сообщение примут, а подписку
`notify_when_idle` молча уронят (проверено: с токеном `peer_idle_notice`
приходит, без токена — тишина). Поэтому токен стоит слать всегда.

Токенов у сессии два: `peerToken` (в key-файле, для других сессий) и
`childToken` (в `CLAUDE_CODE_MESSAGING_TOKEN`, для собственных потомков).

## Сообщение

```json
{"msgV":1,
 "msg_id":"<uuid4>",
 "type":"user",
 "message":{"role":"user","content":"<текст, см. конверт ниже>"},
 "priority":"now|next|later",
 "from":"uds:/run/user/1000/cc-socks/<мой-pid>.sock"}
```

| поле | обязательность | смысл |
|---|---|---|
| `msgV` | нет | версия кадра, сейчас `1` |
| `msg_id` | нет | uuid4; по нему приходят квитанции |
| `message.content` | **да** | непустая строка, иначе кадр молча выбросят |
| `priority` | нет | `next` по умолчанию; `now` — вперёд очереди |
| `from` | нет | обратный адрес; без него сессия видит «unidentified» |
| `session_id` | нет | если указан и не совпал — кадр выбросят |
| `file_attachments` | нет | вложения (не проверялось) |

Сообщение кладётся в очередь как `{isMeta: true, skipSlashCommands: true,
skipAttachments: true}`. Отсюда важное ограничение:

> **Слэш-команды через канал не работают.** `/model`, `/clear`, `/rc` в тексте
> сообщения останутся текстом. Единственный способ выполнить слэш-команду в
> чужой сессии — напечатать её в tmux-пейн (так это и делает `mop doctor`
> при исчерпанной квоте модели).

## Конверт: заявка о режиме прав

Сессия, запущенная с `--dangerously-skip-permissions`, **не отдаёт модели**
сообщение от отправителя, который не заявил свой режим прав. Она кладёт его в
«held»-очередь и рисует человеку диалог «Deliver / Deny». Для слейва без
человека за терминалом это неотличимо от потери сообщения.

Заявка живёт не в полях кадра, а внутри `message.content`:

```
<cross-session-message from="uds:…" from-session="…" hop-chain="…" from-name="…" from-mode="bypass">
тело сообщения
</cross-session-message>
```

* все атрибуты необязательны, но **порядок фиксирован** — именно этот. Приёмник
  разбирает конверт регуляркой и проверяет, что обратная сборка даёт исходную
  строку байт в байт; переставленные атрибуты просто не распознаются, и
  сообщение уезжает в held;
* `from-mode`: `bypass` | `prompting`. Должен совпадать по классу с режимом
  приёмника, иначе held с причиной `mode-mismatch`;
* `from` — тот же `uds:`-адрес, что и в кадре, спецсимволы percent-кодируются
  (`/`, `:`, `.`, `-`, `_` остаются как есть);
* `from-session` — `[A-Za-z0-9_-]{1,80}`, `from-name` — без `"<>` и переводов
  строк, `hop-chain` — до 32 хешей через запятую (защита от петель пересылки).

Причины удержания, которые может назвать приёмник: `no-mode-asserted`,
`mode-mismatch`, `bypass-default`, `explicit-setting`, `managed-setting`,
`repo-setting`, `invalid-setting`.

Второй путь — со стороны приёмника: в его `settings.json`

```json
{"crossSessionInbound": "accept"}
```

Значения: `accept` | `hold` | `refuse`. Managed- и repo-настройки могут только
ужесточить: собственный `accept` их не перебивает.

## Обратный канал

Чтобы получать ответы, надо самому слушать сокет. Адрес проверяют строго:

* тот же каталог сокетов, что у приёмника, **или** каталог из списка
  дефолтных при совпадении uid владельца (фича `reply_across_default_dirs`);
* имя файла — `<pid>.sock`, либо `<pid>-<8 hex>.sock`, либо `<hex>.sock`;
* симлинк в качестве адреса отвергают.

Не прошедший проверку адрес не даёт ошибки — ответ просто не отправляют.

### Квитанции

```json
{"type":"control","action":"peer_message_status",
 "orig_msg_id":"<msg_id сообщения>","status":"held|denied|delivered|refused|expired|dropped"}
```

`dropped` дополнительно несёт `drop_reason` (например `queue-full`) и
`dropped_msg_ids`. Сообщение, доставленное сразу, квитанции может и не породить
— квитанции нужны прежде всего для held-пути.

### «Сессия освободилась»

Подписка:

```json
{"msgV":1,"msg_id":"<uuid4 подписки>","type":"control",
 "action":"notify_when_idle","from":"uds:…","from_mode":"bypass"}
```

Ответ, когда сессия дойдёт до простоя:

```json
{"type":"control","action":"peer_idle_notice",
 "orig_msg_id":"<uuid4 ПОДПИСКИ>","state":"idle",
 "from":"uds:…","from_mode":"bypass","msgV":1,"msg_id":"…"}
```

`orig_msg_id` — идентификатор **подписки**, а не сообщения. Требует auth-кадра.
Подписка одноразовая: notice приходит один раз и снимает её.

### Прочие control-действия

`rename` (сменить имя сессии), `yield_artifact_replies`,
`unyield_artifact_replies`, `artifact_replies_yielded` — прочитаны в бинаре, не
проверялись.

## Что проверено, а что нет

Проверено на живой одноразовой сессии 2026-08-29:

* доставка кадра `type:"user"` и ответ модели на него;
* удержание в held без конверта и автодоставка с `from-mode="bypass"`;
* `notify_when_idle` → `peer_idle_notice` при наличии auth-кадра, и тишина
  без него;
* `CLAUDE_CODE_MESSAGING_SOCKET` / `CLAUDE_CODE_MESSAGING_TOKEN` в окружении
  дочернего процесса сессии.

Не проверялось: `file_attachments`, `hop-chain`, `session_id`, поведение под
`crossSessionInbound: "refuse"`, windows-ветка (там auth обязателен) и
artifact-действия.

## Оговорка про версию

Это внутренний протокол, а не документированный публичный API. Разобран на
`claude` **2.1.251**; поля и гейты могут поменяться в любой версии. Если
`mop send` вдруг перестанет доставлять — проверять в первую очередь конверт
`cross-session-message` и логику held.
